## План и текущее состояние

Данная папка imax-webpush — самостоятельная рабочая копия исходников из Git archive, без .git; ниже приложен patch для переноса в актуальную ветку Cursor.

4. После приёмки — отдельное согласование production.

## VAPID — не SSH

SSH-ключ нужен для подключения к серверу. VAPID идентифицирует отправителя Web Push. Пару создают один раз, используют стабильно. Замена VAPID требует переподписки браузеров. Не менять Android Firebase и GOOGLE_APPLICATION_CREDENTIALS.

Нужны три серверные настройки:

```dotenv
WEB_PUSH_VAPID_PUBLIC_KEY=<публичный ключ>
WEB_PUSH_VAPID_PRIVATE_KEY=<закрытый ключ>
WEB_PUSH_VAPID_SUBJECT=mailto:<реальная почта администратора>
```

Публичный ключ автоматически отдаётся через GET /p/max-service/api/push/web/config. Он не секрет. Закрытый ключ и contact subject браузеру не возвращаются. Пустые/некорректные ключи отключают только Web Push; Android сохраняет прежнюю настройку.

## Подготовка тестового окружения

Не выполнять эти шаги на production без согласования. Для теста предпочтителен отдельный HTTPS hostname и отдельный внутренний секрет, чтобы рабочая 1С не отправляла уведомления тестовым получателям.

1. Установить зависимости из app-max/package-lock.json командой npm ci. Node должен соответствовать используемому runtime проекта (CI — Node 22).
2. Определить реальную контактную почту администратора.
3. Создать отдельный закрытый файл вне Git и web-root, например /etc/itus-max-web-push.env. Команда генератора: `sudo node scripts/generate-vapid.mjs /etc/itus-max-web-push.env mailto:REAL_ADMIN_EMAIL`. Заменить REAL_ADMIN_EMAIL реальной почтой до запуска. Скрипт не печатает ключи, создаёт файл с режимом 600 и отказывается перезаписывать существующий файл.
4. Подключить этот файл через EnvironmentFile к тестовой systemd-службе либо перенести эти три значения в её существующий закрытый env. Не удалять прежние настройки. Для systemd EnvironmentFile файл может читать root, не требуется делать его общедоступным.
5. Сборка: npm test и npm run build. Перезапускать только тестовую службу. Если изменялся unit/drop-in, требуется systemctl daemon-reload, затем restart соответствующей тестовой службы.
6. Открыть HTTPS /p/max-service/api/push/web/config: enabled:true, publicKey заполнен, privateKey отсутствует. При enabled:false проверить наличие и корректность трёх настроек в процессе. /health не подтверждает доставку.
7. Не править WEB_PUSH_VAPID_PUBLIC_KEY вручную в браузерном config — новая реализация получает public key из серверного маршрута.

## iPhone: совместимость и действия

Решает установленная iOS и доступность Web Push API, а не только модель. Минимум — iOS/iPadOS 16.4. Устройства со старой неподдерживаемой системой не смогут получить Web Push; показать инструкцию обновления, не выдавать несуществующий токен.

Safari → сайт I-MAX → Поделиться → На экран «Домой» (в новых версиях также подтвердить открытие как веб-приложения, если предложено). Затем запустить с иконки, авторизоваться, открыть настройки уведомлений, нажать «Подключить Push» и разрешить.

Запрос разрешения вызывается непосредственно нажатием кнопки, без предварительного ожидания сетевого запроса. Настройки и Service Worker подготавливаются заранее. Если настройки ещё не успели загрузиться, интерфейс попросит повторное нажатие. Автоматически запрашивать разрешение при входе приложение не будет.

Обычная вкладка Safari не заменяет запуск с экрана «Домой». При запрете нужно разрешить уведомления в настройках iOS. Проверить режимы фокусирования. При удалении и повторной установке подключить Push заново.

## Яндекс Браузер на Windows

Актуальный обычный профиль, HTTPS, без приватного режима. Авторизоваться, нажать «Подключить Push», разрешить сайту уведомления. Проверить уведомления Яндекс Браузера в Windows, режим «Не беспокоить» и ограничения корпоративных политик.

Веб-приложение устанавливать на рабочий стол для подписки не обязательно. Проверить вкладку в фоне и закрытую вкладку. Получение при полностью завершённом процессе браузера зависит от его фоновой работы и системы — не обещать его по результатам теста с открытым браузером. При необходимости включить поддерживаемую браузером фоновую работу и проверить отдельно.

Если sender отклоняет hostname Push endpoint, показать администратору только hostname. Закрытый URL подписки и её ключи не публиковать. После проверки сервиса точный hostname можно добавить в WEB_PUSH_ALLOWED_HOSTS (через запятую); не добавлять localhost/IP/неизвестные домены. По умолчанию разрешены web.push.apple.com и поддомены push.apple.com, fcm.googleapis.com, updates.push.services.mozilla.com, push.yandex.ru.

## Приёмочный сценарий

Для одного тестового пользователя подключить Android, iPhone с экрана «Домой» и Яндекс Windows. Подтвердить три независимые регистрации в 1С. Отправить сообщение и назначение: для Android прежний /api/push/dispatch, для Web новый /api/push/web/dispatch. Убедиться, что получен системный Push, а не только toast или результат poll.

Проверить краткий/длинный текст, переход в чат и заказ, холодный запуск с авторизацией, повторное событие, отзыв разрешения, выход и смену пользователя. При выходе браузерная подписка отзывается; при входе существующая подтверждается в 1С. Истёкшие записи удаляются по результату sender.

Проверить старый Android APK отдельно: серверная Web Push-доработка не требует обновления APK. Новая веб-версия не изменяет native-push.js и Android resources.

Результаты фиксировать без содержимого сообщений, endpoint, токенов и секретов: платформа/версия, сценарий, время, eventId теста, sent/failed, системное отображение, результат перехода. Успешный HTTP sender — не подтверждение появления уведомления.
