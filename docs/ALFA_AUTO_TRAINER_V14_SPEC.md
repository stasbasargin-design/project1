# Технический план v14 — визуально достоверный WEB-тренажёр 1С:Альфа-Авто 6.1

Статус: спецификация для разработки и проверки. Дата: 18.11.2026.
Проект: «Инструкция для пользователей». Роль: мастер-приёмщик (первая линия).
Главный принцип: **визуально узнаваемая 1С и настоящие действия пользователя вместо обычного веб-квеста**.

## 1. Цель и границы
1. WEB-тренажёр воспроизводит расположение, названия, порядок работы и поведение форм доработанной 1С:Альфа-Авто 6.1 максимально близко к доступным эталонным экранам.
2. Вновь создаваемые документы/карточки НЕ содержат заранее введённых учебных ответов. Пользователь вводит данные и выбирает значения из справочников сам.
3. Справочники содержат **учебные записи**, но значения не выбираются за ученика. Исключение — штатное автоматическое заполнение 1С по телефонному звонку, выбранному контрагенту, договору, связанному документу или другому явному триггеру.
4. Тренажёр не подключается к боевой базе 1С, не отправляет письма/SMS/MAX, не меняет рабочие данные.
5. Исходный v13.1 и его интерфейсные экраны, сценарии, видео, экзамены и контракты нельзя заменить упрощённой демонстрацией. Любые несовместимые изменения фиксируются отдельно.
6. Прототип `trainer-preview/index.html` из предыдущей ветки не является исходной базой визуального редизайна.
7. **Блокер:** оригинальный ZIP v13.1 обнаружен в библиотеке, но доступ к исходным байтам сейчас отсутствует. Восстанавливать «оригинальные скрипты/видео» по одному манифесту нельзя. Первое действие перед полным рефакторингом — получить оригинал, проверить SHA-256 и создать неизменяемый snapshot.

## 2. Эталон внешнего вида
Источники для реконструкции:
- «CRM Событие и система задач (1).pdf» — реальные формы рабочего стола, «Событие», «Задача CRM», диалоги, окна выбора, вид обращения, привязка документов;
- «Инструкция_мастера-приемщика_1С_Альфа-Авто_6.1(2).docx» — последовательность действий и формы;
- «Работа КП(1).docx» — калькуляция, автоработы, товары, подбор, проценка, печатные формы, согласование;
- «Инструкция создания автомобиля(1).docx» и «регламент заполнение карточки автомобилей.docx» — карточка автомобиля, VIN/шасси, комплектации;
- «Создание карточки Контрагента.docx» — форма контрагента, поиск ИНН;
- «Изменения в задаче CRM.docx» — поля дат КО и «Общий вопрос»;
- «Автоматическая КП по дефектовке.docx» — автоматическое создание КП и цепочка задач;
- «Инструкция по работе с экспресс заказ.docx», «Работа с мессенджером «MAX» .docx», «Инструкция по работе с заблокированными контрагентами ФРОНТЛАЙН.docx», «Инструкция Отправка Email из 1с.docx».

Требования к визуальному слою:
- Воссоздать плотную рабочую область 1С: верхняя панель навигации, панель команд, вкладки, подписи полей, рамки списков, табличные части, сообщения, модальные формы выбора.
- Расположение и размеры элементов сравнивать с настоящими скриншотами, а не проектировать новое UI «по мотивам».
- Интерфейс обязан быть управляемым: поля — настоящие input/select/датапикеры, строки — выбираемые, кнопки — рабочие.
- Не превращать весь интерфейс в статичный скриншот с невидимыми зонами, если это мешает вводу/поиску/прокрутке.
- Встроенные подсказки доступны отдельным слоем и отключаемы; в режиме экзамена не показывать правильные ответы в форме.
- Для одинаковых диалогов и контролов использовать один переиспользуемый компонент: выбор из списка, поиск, карточка, таблица, уведомление, календарь.
- Экран по умолчанию ориентирован на типичное разрешение рабочего места; на меньшем экране допустима прокрутка, но не изменение порядка полей.

## 3. Нормы предзаполнения
### Пустая форма при ручном создании
- «Событие» при ручном создании, «Задача CRM», новая карточка контрагента, новая карточка автомобиля, новые строки авторабот/товаров — без готовых ответов.
- Поля системного происхождения (дата создания, текущий пользователь, присвоенный системой номер и др.) имитировать только когда это подтверждено реальной 1С.
- Списки справочников могут содержать учебные контрагентов/контакты/автомобили/работы, но не создавать эффект «контрагент уже выбран».

### Подстановка после действия/триггера
- «Событие» из входящего звонка: вид «Входящий звонок» и номер телефона система задаёт автоматически; существующий контакт определяется по учебному справочнику при совпадении.
- «Событие» из исходящего звонка: вид и при наличии исходный документ устанавливаются системой.
- «Договор» выбирается автоматически после подтверждения контрагента и организации, если это предусмотрено реальным процессом.
- Авто-КП: заполнение реквизитов из исходного ЗН и создание задачи после системного завершения дефектовки моделируются только в этом маршруте.
- При каждом запуске урока — новый независимый снимок состояния, возможность «Сбросить учебный сценарий» без потери истории экзаменов.

## 4. Реестр экранов, ожидаемое взаимодействие, проверки

### P0 — первый демонстрируемый вертикальный срез
1. **Рабочий стол первой линии CRM.** Реальные зоны «Не разобранное», «Подготовка к визиту», «Сделка», список задач, фильтр «Ответственные», визуальные состояния, двойной клик по строке. Ученик сам выбирает ответственных, открывает задачу группы и принимает её: появляется подтверждение «Принять документ к исполнению?», ответственный меняется.
2. **Событие.** Реальный порядок полей и блоков: вид обращения, контактное лицо, телефон, контрагент, договор, причина обращения (классификация), «Договоренность с клиентом» (развёрнутый ввод), автомобиль и привязки, прежние обращения, создание сделки/задачи, проведение/отмена. Причина не подменяет договорённость. При исходящем/входящем звонке автоматический вид; при ручном — «Встреча». Вводить данные самому, включая использование Tab. Проведение проверяется по допустимым исходам: продолжение сделки, передача задачи, повторное обращение/привязка или отмена с причиной.
3. **Задача CRM.** Поля ответственного, вида задачи, темы, содержания, сроков, кнопки записи/завершения. Условия отображения полей «Дата записи предлагаемая», «Дата записи желаемая» и «Общий вопрос»: ответственный КО + вид «Телефонный звонок» + тема «Телефонный звонок клиенту». Даты — в интервале от текущего дня до +60 суток; при «Общий вопрос» даты необязательны, но содержание обязательно. Не создавать произвольную форму вместо формы 1С.
4. **Справочник «Контрагенты и контакты» и карточка.** Реальный список с поиском, строками, кнопками «Создать», «Выбрать», «Показать все» и формой карточки. Поиск ИНН/наименования, выбор компании, самостоятельное указание контактных данных; для ИП последовательность формы собственности и «Найти и заполнить» соответствует инструкции. Нельзя заранее выбирать клиента.
5. **Справочник «Автомобили» и карточка.** Поиск по госномеру/VIN/номеру шасси, выбор из таблицы и отдельная карточка с маркой, моделью, вариантом комплектации, госномером, VIN, пробегом, годом и номером агрегата (когда применимо). Вариант комплектации выбирается по ДВС/КПП. Проверки формата и допустимых значений; автоматический подбор марки/модели — только при соответствующем учебном условии и включённом имитаторе этой доработки.

### P1 — калькуляция и обычный ремонт
6. **Калькуляция (КП).** Реквизиты контрагента/договора/автомобиля/способа оплаты; вкладки «Автоработы» и «Товары»; «Добавить», «Подбор», «Показать все», связанные работы/детали и количество; остаток/поставщик/срок поставки; «Проценить», «Заказать»; статус «Согласование», согласование/рекомендация/деталь клиента. Ученик самостоятельно заполняет строки. Нельзя считать шаг завершённым после одной кнопки, если по регламенту требуется проверка.
7. **Заказ-наряд и стандартная сделка.** Перенос согласованных работ/товаров из КП, вкладки ЗН, результат ремонта, допуски на завершение и привязки. Не заменять форму ЗН «обобщённой карточкой».
8. **Автоматическая КП после дефектовки.** Системное уведомление → КП и задача мастеру → принять → заполнить/проценить → «Согласование» → задача согласования клиенту; ответственные, результаты, комментарий и завершение. Защита от дублей. Этот маршрут не должен менять обычную калькуляцию.

### P2 — остальные существующие разделы
9. **Экспресс ЗН.** Три маршрута: мойка, агрегат, субподряд — с их реальными ограничениями и диалогом выбора. Для экспресс-маршрута не создаются обычные КП/план ремонта.
10. **MAX.** Приглашение из события/КП/чата, выбор контрагента и контакта через справочник, проверка согласия на ПД; без настоящих отправок.
11. **Заблокированный контрагент.** Реальная форма предупреждения с поведением «Да/Нет/Отмена»; вкладка «Разблокировка», сумма, комментарий, запрос, имитация решения и уведомления.
12. **Email из 1С.** Печатная форма → кнопка отправки → выбор PDF → окно письма (отправитель, получатель, тема, вложение, текст) → имитация отправки с записью в учебное дерево сделки.

## 5. Обучение, видео, сценарии
- Сохранить **8 существующих уроков** и **4 экзамена** из v13.1. Изменить слой взаимодействия, а не заменять их викториной.
- В уроке — этапы и необязательные подсказки, неверный ввод подсвечивается; ошибки подсказывают проблему, но не вставляют ответ.
- В экзамене — самостоятельное выполнение на форме 1С; учитывать ошибочные действия, подсказки, фиксировать результат 0–100 и историю попыток; выгрузка CSV.
- Если автор/источник учебных видео доступен: сохранить **3 оригинальных MP4 и VTT**, проверить загрузку и синхронность субтитров. Если исходники недоступны — явно отразить отсутствие, не имитировать их наличия.
- Кейс 1: новый клиент, ручная встреча, контрагент, автомобиль, событие, последующий документ.
- Кейс 2: входящий звонок от известного клиента, выбор существующей записи, договорённость, запись на ремонт.
- Кейс 3: передача в КО с заполнением дат и отдельный «Общий вопрос».
- Кейс 4: подготовка КП по дефектовке, проценка ОЗЧ и согласование.

## 6. Структура реализации (целевая)
- Ветка разработки отдельно от `main`; оригинальный v13.1 хранить неизменяемо как исходный эталон.
- UI: `shell` 1С / `forms` / `references` / `tables` / `dialogs`.
- Данные: отдельные `fixtures` (учебные записи в справочниках) и `scenario-initial-state` (начальные значения полей, чаще пустые), не смешивать.
- Правила: декларативные `scenario-steps` + `validation`; обучение и экзамен используют одни и те же рабочие формы.
- Сценарии не обращаются к рабочим API. Из `config` режим только `demo`.
- Состояние документа изменяется только действием ученика или документированным автоматическим триггером; поддержать отмену, восстановление и повторное прохождение.
- Все изменения сопровождать тестами, документом о визуальных отличиях и снимками экрана «эталон / тренажёр».

## 7. Приёмочные критерии
A. Все 12 экранов открываются; каждая необходимая команда, табличная строка и окно выбора работает; `index.html` есть и запускается.
B. Пять экранов P0 сопоставлены со скриншотами настоящей 1С; вкладки/подписи/порядок/координаты полей проверены вручную. Формулировка «один в один» допустима только после приёмки; пока используется «визуально близко».
C. Новые карточки и документы не содержат заранее введённых ответов. Подстановки работают только после подтверждённых триггеров.
D. Справочники имеют рабочие поиск, фильтр, выбор, отмену, ввод с клавиатуры; выбранное значение попадает в нужное поле, но само открытие справочника ничего не выбирает.
E. Выполнены сквозные тесты 4 кейсов из §5 (включая проверки ошибочных действий), тест возврата и сброса.
F. Все 8 уроков и 4 экзамена доступны; история экзамена сохраняется, CSV скачивается без повреждений.
G. Все 3 оригинальных видео и VTT проверены *только после восстановления исходных файлов*.
H. Отдельная тестовая публикация; боевые URL/БД/данные не изменены. Пользователь проверяет прямую ссылку и принимает визуал.

## 8. Порядок реализации и ограничения
1. Восстановить/верифицировать исходный ZIP v13.1 из доступного оригинала и проверить манифест/видео.
2. Сверить эталонные изображения с доступными экранными инструкциями и тестовой 1С, описать расхождения.
3. Сначала создать P0 (рабочий стол → событие → задача → контрагент → автомобиль) как полноценный сквозной интерактивный сценарий с пустыми формами.
4. Продемонстрировать визуальные скриншоты и ввод данных, провести приёмку P0.
5. Перенести на новую оболочку оставшиеся существующие формы и процессы P1/P2, не меняя содержательную логику.
6. Восстановить видео и экзамены, запустить smoke + browser regression, опубликовать независимую тестовую версию.
7. Только после отдельного одобрения — обсуждать производственную публикацию (не автоматическая часть плана).

## 9. Что НЕ считается результатом
- «Тренажёр» как набор плиток «выбери правильное действие»;
- просто скриншоты с неработающими кнопками;
- постоянные готовые значения полей, которые ученик должен заполнять;
- утверждение о точном визуальном совпадении без сравнения с эталоном;
- выдача неполного прототипа без видео за оригинальную v13.1.
