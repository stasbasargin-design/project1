# I-MAX: доработка 1С для Web Push (iPhone и Яндекс Браузер Windows)

Дата: 20.10.2026. Код подготовлен локально на основе project1 commit a076c44. Не опубликован в production. Android остаётся на существующем FCM; Web Push — отдельный транспорт. Исходники конфигурации 1С недоступны: реализовать перечисленные изменения должен разработчик 1С.

## 1. Регистрация устройств

Существующий POST /notifications/push/subscribe должен принимать два формата, не заменяя один другим.

Android, без изменений:

```json
{"platform":"android","token":"<FCM token>","clientInstanceId":"<UUID>"}
```

Web (iPhone с экрана «Домой», Яндекс на Windows):

```json
{
  "platform":"web",
  "clientInstanceId":"<UUID>",
  "subscription":{
    "endpoint":"https://<push-provider>/<private-endpoint>",
    "keys":{"p256dh":"<browser-public-encryption-key>","auth":"<browser-auth-secret>"}
  }
}
```

Оба запроса дополняются существующими общими полями авторизации: userId/maxUserId/authId, authMode, requestId, timestamp, max и т. д. Пример пользователя для теста — 13970179. Эти поля не заменяют проверку авторизации. Связать регистрацию с текущим проверенным пользователем; не разрешать регистрацию от имени произвольного userId.

Успешный ответ обязателен именно с boolean registered:

```json
{"success":true,"data":{"registered":true}}
```

Регистр хранит пользователя, platform, clientInstanceId, active, даты и либо token, либо полную subscription. У пользователя одновременно могут быть несколько Android, iPhone и браузеров. Новая подписка не должна затирать другие устройства. Повтор одного endpoint/установки обновляет запись. При входе другого пользователя на той же установке атомарно убрать старую привязку этого endpoint и создать новую, не затрагивая остальные устройства.

Не преобразовывать endpoint в FCM token. p256dh/auth — не VAPID-ключи. Не логировать endpoint, token, auth и заголовки авторизации.

POST /notifications/push/unsubscribe принимает тот же Web-формат. Деактивировать только подписку текущего пользователя. Идемпотентный ответ:

```json
{"success":true,"data":{"removed":true}}
```

При входе браузер повторно подтверждает имеющуюся подписку без нового запроса разрешения. При выходе отправляет unsubscribe и отзывает браузерную подписку даже при ошибке ответа 1С. Серверная запись, оставшаяся после сетевой ошибки, очищается после 404/410 от провайдера. Регистрация должна подтверждать фактическую запись, а не всегда возвращать registered=true.

## 2. Отправка событий

После фиксации бизнес-операции создать событие с постоянным eventId, определить адресатов по правам и выбрать все их активные устройства. Включить существующие правила выбора получателей и настроек уведомлений. Сообщение не должно автоматически отправляться самому автору.

Для Android продолжать существующий вызов:

`POST https://ea-itus.ru/p/max-service/api/push/dispatch`

Формат tokens, title, body, data сохраняется. Не отправлять Android повторно через новый канал.

Для Web использовать новый отдельный маршрут:

`POST https://ea-itus.ru/p/max-service/api/push/web/dispatch`

Заголовки: Content-Type: application/json; Authorization: Bearer <PUSH_INTERNAL_TOKEN>. Секрет тот же внутренний серверный, не SSH-ключ и не VAPID. Передаётся только между 1С и Node.

```json
{
  "subscriptions":[
    {"endpoint":"https://<provider>/<endpoint>","keys":{"p256dh":"<key>","auth":"<secret>"}}
  ],
  "title":"I-MAX",
  "body":"Новое сообщение",
  "data":{
    "type":"new_messages",
    "topicRef":"<идентификатор клиентской переписки>",
    "eventId":"<стабильный UUID события>"
  }
}
```

Назначение: data.type=executor_assigned и orderRef. Внутренний чат: internal_chat_message и topicRef. Выходной контроль: quality_control_requested и orderRef. Использовать идентификаторы, которые принимают существующие методы открытия объектов. Все data-поля — строки. Node сохраняет только поля маршрутизации type,eventId,topicRef,topicId,orderRef,orderId; произвольные url/icon и HTML из data не используются.

Передавать до 50 уникальных subscriptions за пакет. Дубликаты endpoint отклоняются, не переупорядочиваются. Номера индексов ответа относятся к исходному массиву subscriptions. Большую аудиторию делить на пакеты; Android имеет отдельный прежний лимит.

body обязателен. Отправлять краткий обычный текст без персональных подробностей, файлов и секретных ссылок. Node применяет существующее HTML-to-text и ограничение текста; итоговый Web Push payload не больше 3500 байт UTF-8. Если он всё ещё больше — 400 PAYLOAD_TOO_LARGE. Полный текст сообщения остаётся в приложении.

## 3. Ответ и очередь

Пример частичного успеха:

```json
{
  "success":true,
  "data":{
    "sent":1,
    "failed":2,
    "invalidSubscriptionIndexes":[1],
    "retryableSubscriptionIndexes":[2],
    "errors":[{"index":1,"status":410},{"index":2,"status":503}]
  }
}
```

Индексы нулевые. sent означает принятие сервисом доставки, а не показ на экране. HTTP 200 не означает успех всех адресатов.

- 404/410 у отдельной подписки: деактивировать эту запись; не удалять другие устройства пользователя.
- 429/5xx/сетевой сбой (status=0): повторять только соответствующие подписки с задержкой и ограничением попыток.
- 400/401/403 провайдера: не удалять автоматически; проверить ключи/формат/настройки. errors содержит только индекс и статус, без приватного ответа провайдера.
- HTTP 401 всего маршрута: внутренний секрет не совпал/не передан.
- HTTP 503 WEB_PUSH_NOT_CONFIGURED: сервер не настроен; сохранить событие в очереди, уведомить администратора.
- HTTP 400 INVALID_SUBSCRIPTION: невалидные поля или endpoint не входит в разрешённые сервисы. Не повторять бесконечно; исправить данные/настройку.

Очередь должна работать после транзакции, чтобы Push-сбой не откатывал бизнес-операцию. Идемпотентность создания eventId и контроль повторов — в 1С. Node не хранит очередь и не гарантирует exactly-once. При сетевой неопределённости допускается повтор, поэтому сохранять тот же eventId. Service Worker использует tag на основе eventId и не запрашивает повторный звук для замены уже отображённого уведомления, но это не гарантирует дедупликацию после удаления уведомления пользователем.

## 4. Подписки и адреса

Подписки принимает 1С по прежней базе HTTP-сервиса. Веб-клиент обращается через /p/max-service/api/1c. Фактический upstream определяется ONE_C_TARGET (подтверждённая ранее база: https://1c.eazia.ru/aa6_ea_test9/ru/hs/max-service).

Новый Node Web Push sender допускает HTTPS endpoints Google FCM, Apple Push, Mozilla и push.yandex.ru. Если реальный Яндекс Браузер вернул иной endpoint, передать администратору только hostname, без пути/ключей. Администратор проверяет принадлежность провайдеру и добавляет точный hostname в WEB_PUSH_ALLOWED_HOSTS. Не отключать проверку хоста и не разрешать произвольные URL.

## 5. Приёмка с разработчиком

1. Один пользователь имеет Android и Web-подписку, обе активны.
2. Повтор subscribe не даёт дубль; смена пользователя не оставляет endpoint у прежнего аккаунта.
3. Сообщение и назначение создают события, отправляются соответствующими транспортами.
4. Android остаётся рабочим; iPhone и Яндекс получают уведомления в системном интерфейсе.
5. Тап/клик открывает нужный объект после входа, права доступа проверяются прежними методами 1С.
6. Невалидная Web-подписка не останавливает Android и другие подписки.
7. Удаление/повторная установка веб-приложения даёт новую корректную регистрацию.

Проверку физической доставки выполнять на тестовом окружении с согласованными устройствами. Production ещё не менялся.
