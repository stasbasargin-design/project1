# I-MAX: работа с двух компьютеров и выпуск версий

## Принцип

У каждого разработчика и Cursor — собственный GitHub-аккаунт, SSH-ключ и отдельный локальный клон. Единственный источник кода — GitHub; production изменяется только release-коммитом из `main` через штатный GitHub Actions workflow.

Не используйте общий токен, общий SSH-ключ, общую рабочую папку или общую feature-ветку.

## Одно изменение — одна версия

Для каждого изменения пользовательского поведения владелец задаёт следующую версию до начала release-подготовки. Номер назначается только после проверки фактического production SHA и версии на Timeweb.

Перед выпуском должны совпадать:

- runtime-версия I-MAX в `app-max/assets/app.js`;
- npm-версия в `app-max/package.json` и `package-lock.json`;
- Android `versionName` и увеличенный `versionCode` в `app-max/android/app/build.gradle`;
- номер и SHA в release-заявке.

Если эти значения уже расходятся, release не начинается. Сначала отдельной задачей фиксируется подтверждённая production-база. Нельзя угадывать версию по файлу, имени APK или старой заявке.

## Роли

### Автор изменения — компьютер A

1. Выполняет `git fetch --prune origin`.
2. Создаёт одну ветку от `origin/main`: `feature/<задача>` или `fix/<задача>`.
3. Делает только заявленное изменение, обновляет версию для продукта и release-заявку.
4. Выполняет `npm ci`, `npm test`, `npm run build`.
5. Коммитит, отправляет свою ветку и передаёт второму Cursor заполненную команду из шаблона.

### Проверяющий и релиз-координатор — компьютер B

1. Не редактирует работу автора «поверх» его локальной папки: получает ветку из GitHub в свой клон.
2. Проверяет точные SHA, версию, diff и проверки заново.
3. Создаёт/обновляет PR без добавления посторонних коммитов.
4. До явного подтверждения владельца не вливает PR, не пушит `main` и не запускает production workflow.
5. После подтверждения использует штатный PR/merge-процесс. Push release-коммита в `main` запускает существующие `Deploy MAX Service` (Timeweb) и `Build I-MAX Android APK` (APK).
6. Проверяет статус обоих GitHub Actions, скачивает APK только из запуска, привязанного к release SHA, и выполняет health-check/функциональную проверку.

## Защита `main`

Владелец репозитория включает branch protection для `main`: pull request, review, обязательные `npm test`/build checks и требование актуальной ветки перед merge. GitHub поддерживает эти правила в настройках protected branches.

## Откат

До release сохраняется предыдущий production SHA и результат health-check. При сбое выпуск останавливается; откат выполняется только штатной процедурой Timeweb после подтверждения владельца. Не делайте ручной copy/deploy и не откатывайте произвольный commit.
