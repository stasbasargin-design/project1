# Доработка API 1С для I MAX

## Назначение

Документ описывает методы 1С, которые нужны для новых экранов I MAX: поиск заказ наряда по госномеру, отображение пробега, история обслуживания без PDF и решение технолога по выезду.

Базовый URL в production:

`https://1c.eazia.ru/aa6_ea_test9/ru/hs/max-service`

Все методы принимают и возвращают JSON в UTF 8. Только `POST`. Пользователь и права определяются 1С из авторизационного контекста запроса; не доверять роли, employeeRef, orderRef и vehicleRef из тела без серверной проверки доступа.

## Обязательные заголовки

| Заголовок | Кто задаёт | Назначение |
| --- | --- | --- |
| `Content-Type: application/json; charset=utf-8` | I MAX | JSON |
| `X-ITUS-Request-Id` | I MAX | трассировка одного запроса |
| `X-ITUS-Token` | сервер Timeweb | общий секрет интеграции |

`X-ITUS-Token` не приходит из браузера. Node.js-прокси на Timeweb читает `ONE_C_TOKEN` из `/etc/itus-max.env` и добавляет заголовок перед обращением к 1С. При неверном или отсутствующем токене вернуть `401` и JSON-ошибку, не HTML.

## Единый формат ответа

Успех:

```json
{ "success": true, "data": {} }
```

Ошибка:

```json
{
  "success": false,
  "error": {
    "code": "ACCESS_DENIED",
    "message": "Нет доступа к заказ наряду"
  }
}
```

Использовать HTTP: `400` неверные данные, `401` токен или авторизация, `403` нет прав, `404` объект или метод отсутствует, `409` конфликт, `422` бизнес-валидация, `500` внутренняя ошибка.

## 1 Поиск заказ наряда

`POST /orders/search`

Доступ: МП, исполнитель, технолог, администратор. Искать только среди ЗН, доступных текущему пользователю.

Запрос:

```json
{
  "requestId": "uuid",
  "userId": "13970179",
  "search": "А000АА72",
  "searchBy": ["orderNumber", "vehiclePlate", "counterparty"]
}
```

`search` ищет по номеру ЗН, госномеру и контрагенту. Поиск без учёта регистра; поддерживается частичное совпадение. Максимум 50 элементов, сначала точные совпадения.

Ответ:

```json
{
  "success": true,
  "data": {
    "orders": [
      {
        "orderRef": "ORDER_GUID",
        "orderNumber": "РИЦ-З22752",
        "vehicle": { "vehicleRef": "VEHICLE_GUID", "model": "КАМАЗ 54901", "plate": "А000АА72" },
        "counterparty": { "ref": "CLIENT_GUID", "name": "Контрагент" },
        "mileage": 184500,
        "status": { "code": "in_progress", "title": "В работе" }
      }
    ]
  }
}
```

## 2 Пробег текущего заезда

Пробег в I MAX только отображается, пользователи не могут его менять. Отдельный метод записи не требуется.

1С должна возвращать актуальное поле `mileage` в `/orders/list`, `/orders/get` и `/orders/search`. Значение берётся из реестра 1С для текущего заезда и показывается как справочная информация.

## 3 История обслуживания без PDF

`POST /quality/service-history`

Доступ: технолог и администратор; дополнительно проверить доступ к текущему автомобилю. Метод только читает данные. Не возвращать вложения, base64, чат и возможность добавлять комментарии.

Запрос:

```json
{
  "orderRef": "ORDER_GUID",
  "vehicleRef": "VEHICLE_GUID",
  "vehiclePlate": "А000АА72",
  "mileage": 184500
}
```

`mileage` — актуальный пробег выбранного ЗН из реестра 1С. Поле передаётся для трассировки и проверки согласованности данных; историю нужно определять по `vehicleRef`, а не по пробегу.

Ответ:

```json
{
  "success": true,
  "data": {
    "visits": [
      {
        "orderRef": "PREVIOUS_ORDER_GUID",
        "orderNumber": "РИЦ-З201138",
        "closedAt": "2022-03-11T10:29:10+05:00",
        "mileage": 172340,
        "reason": "Течь УР, замена рулевых наконечников",
        "goods": ["Наконечник рулевой", "Хомут"],
        "works": ["Мойка автомобиля грузового", "ГУР - поиск неисправности"],
        "recommendations": "Рекомендуется замена механизма ГУР"
      }
    ]
  }
}
```

Список сортировать от последнего завершённого заезда к раннему. Если истории нет, вернуть успешный ответ с пустым `visits`.

Старый `/quality/service-history/pdf` можно сохранить для других потребителей, но приложение I MAX больше его не вызывает.

## 4 Решение выходного контроля

Существующий метод `POST /quality/complete` должен принимать решение технолога.

Дополнение к запросу:

```json
{
  "orderRef": "ORDER_GUID",
  "documentRef": "QUALITY_GUID",
  "surveyRef": "SURVEY_GUID",
  "surveyVersion": "1",
  "result": "passed",
  "answers": { "result": "passed" },
  "formValues": {}
}
```

Допустимые значения `result`:

- `passed` — кнопка «Выезд разрешен»;
- `failed` — кнопка «Выезд запрещен».

1С должна записывать решение, автора и время. Если запрещён выезд, заказ наряд не должен автоматически получать состояние «готов к выдаче». В ответе вернуть подтверждённое значение:

```json
{ "success": true, "data": { "documentRef": "QUALITY_GUID", "completed": true, "result": "passed" } }
```

## 5 Уведомления о назначении исполнителя

`POST /notifications/poll` уже используется приложением. Для назначения исполнителя возвращать тип строго в одном из вариантов:

```json
{
  "eventId": "EVENT_GUID",
  "type": "executor_assigned",
  "title": "Назначен ЗН",
  "message": "Откройте заказ наряд",
  "orderRef": "ORDER_GUID",
  "createdAt": "2026-10-12T10:30:00+05:00",
  "payload": {}
}
```

Клиент также временно понимает прежнее значение `Executor assigned`, но 1С следует вернуть к `executor_assigned`. Событие выдаётся только назначенному исполнителю, ровно один раз, после успешного `/executor/assign`.

## Проверка перед передачей

1. Вызвать каждый новый метод с корректным `X-ITUS-Token` и получить `200` JSON.
2. Повторить без токена и получить `401` JSON.
3. Повторить для пользователя без прав и получить `403`.
4. Проверить поиск по ЗН, госномеру и контрагенту.
5. Проверить, что пробег возвращается в `/orders/list`, `/orders/get` и `/orders/search` и отображается только для чтения.
6. Проверить, что история возвращает только данные прошлых заездов, включая пробег каждого заезда, без файлов и без разрешений на редактирование.
7. Проверить `passed` и `failed` в выходном контроле и отражение результата в 1С.
