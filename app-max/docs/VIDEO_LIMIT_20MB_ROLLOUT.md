# План согласованного увеличения лимита видео до 20 МиБ

Кандидат клиента разделяет лимиты: фото 15 МиБ, видео 20 МиБ, документы 15 МиБ. Выпуск видео-лимита блокируется до подтверждения всей цепочки; одного изменения JavaScript недостаточно.

## Проверенные ограничения

- Nginx для `max-test.ea-itus.ru`: `client_max_body_size 100m`.
- Node тестового сервиса: `MAX_REQUEST_BYTES=31457280` (30 МиБ), `PROXY_TIMEOUT_MS=35000`.
- Файл 20 МиБ превращается в Base64 примерно в 26.67 МиБ; с JSON-конвертом остаётся запас до 30 МиБ. Файл заметно больше 20 МиБ уже опасно приближается к Node-пределу.
- Клиент читает файл в память для Base64. Ограничение проверяется до `FileReader`, поэтому превышающий предел файл не вызывает кодирование и не исчезает молча.
- IndexedDB хранит подготовленные пакеты очереди. На мобильном устройстве необходимо проверить свободное место и устойчивость при нескольких видео; автоматическое перекодирование не входит в задачу.
- Фактические ограничения и таймаут HTTP-сервиса 1С пока не подтверждены.

## Серверный этап до выпуска

1. Разработчик 1С подтверждает приём JSON не менее 28 МиБ для `/defects/entries/add` и обоих чатовых методов, либо сообщает меньший предел.
2. На тестовом контуре отправить видео 19.9 МиБ и 20.1 МиБ на согласованный тестовый ЗН/чат. Проверить время обработки и отсутствие усечения Base64.
3. Если обработка приближается к 35 секундам, отдельно согласовать `PROXY_TIMEOUT_MS=90000` и соответствующие `proxy_read_timeout`/upstream timeout. Не менять только один слой.
4. Проверить свободное место/лимиты временных данных 1С и повтор с тем же idempotency ID после потери ответа.
5. Только после успешной проверки включать клиент с 20 МиБ в release-кандидат. При отрицательном результате вернуть `MAX_VIDEO_UPLOAD_BYTES` к подтверждённому пределу.

Production-конфигурация этим планом не изменяется автоматически.
