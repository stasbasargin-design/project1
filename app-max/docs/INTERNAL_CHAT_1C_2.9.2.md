# Контракт для разработчика 1С: I-MAX 2.9.2

Статус: требуется реализация и приёмка в тестовой 1С. Наличие методов в опубликованной базе не подтверждено. Клиент не показывает новые действия, пока 1С явно не объявит их поддержку. До этого обычные сообщения и вложения работают по прежнему контракту.

## Что уже входит из 2.9.1

Рост поля ввода в двух мессенджерах; просмотр фото/видео над дефектовкой без закрытия ведомости; выбор текста/фото дефектовки МП и пересылка обычными новыми сообщениями в явно выбранный клиентский чат. Эти функции не требуют новых методов 1С.

## Границы нового изменения

Ответы и реакции — только внутренний чат сотрудников I-MAX. Клиентский бот MAX/Telegram не получает новые поля ответов и реакций. В оба мессенджера можно вставлять обычные Unicode-эмодзи в текст.

## Объявление поддержки

В существующем ответе `POST /auth/max`, внутри `data`, добавить только после реализации:

```json
{"chatCapabilities":{"internal":{"replies":true,"reactions":true}}}
```

Отсутствующие или false-флаги отключают только соответствующие новые действия. Состав ролей/вкладок, существующие поля авторизации и запросы не меняются.

## Ответ на сообщение

В существующих `POST /internal-chat/messages/send` и `POST /internal-chat/files/send` поддержать необязательное поле `replyToMessageRef` — настоящий `messageRef` исходного сообщения этой же группы/личной переписки. Обычный запрос без поля обрабатывается по прежнему контракту.

```json
{"groupRef":"GROUP_GUID","groupId":"GROUP_GUID","clientMessageId":"STABLE_UUID","text":"Ответ сотрудника","replyToMessageRef":"ORIGINAL_MESSAGE_GUID"}
```

Для файла сохраняются существующие `kind` и `file`, вместо `text`; правило `replyToMessageRef` такое же. До записи проверить доступ сотрудника к чату и принадлежность исходного сообщения этому чату. Запрещена ссылка на сообщение другой группы/клиента. После удаления исходного сообщения история ответа сохраняется с безопасной заглушкой, без открытия чужих данных.

Идемпотентность существующих `clientMessageId` и `requestId` сохраняется, включая ответ с вложением/S3. При потере HTTP-ответа повтор не создаёт новое сообщение или файл. Поле ответа сохраняется вместе с сообщением транзакционно.

В `/internal-chat/messages/list` и ответе отправки возвращать связь:

```json
{"messageRef":"REPLY_GUID","authorName":"Сохранённый автор ответа","text":"Ответ сотрудника","replyToMessageRef":"ORIGINAL_MESSAGE_GUID","replyTo":{"messageRef":"ORIGINAL_MESSAGE_GUID","authorName":"Сохранённый автор оригинала","text":"Краткий текст оригинала","fileName":"Фото.jpg"}}
```

`authorName` всегда определяется по сохранённому отправителю, не по текущему читателю. Содержимое файла для цитаты не требуется. Дополнительного скачивания всех вложений/всех историй ради цитаты быть не должно.

## Реакция сотрудника

Новый метод `POST /internal-chat/messages/react`:

```json
{"groupRef":"GROUP_GUID","groupId":"GROUP_GUID","messageRef":"MESSAGE_GUID","emoji":"👍"}
```

Общие поля авторизации, `requestId` и `X-ITUS-Request-Id` передаются штатно. Приложение сохраняет requestId для повторной попытки той же неподтверждённой операции.

Операция означает **установить точное значение**, а не переключить его. Одна реакция сотрудника на сообщение; повтор такого же значения не меняет счётчик. Другой эмодзи заменяет прежний, пустая строка `emoji: ""` снимает реакцию. Допустимые значения: `👍`, `❤️`, `😂`, `😮`, `😢`, `🙏`, `✅`, `👎`, `""`. Сохранять Unicode без изменения variation selector.

Сотрудник определяется по проверенной авторизации. Проверить доступ к группе и принадлежность сообщения. Уникальность записи: сотрудник + messageRef внутри данной базы; изменения выполнять транзакционно. Повтор requestId возвращает исходный результат и не увеличивает счётчик.

Успешный ответ:

```json
{"success":true,"data":{"messageRef":"MESSAGE_GUID","myReaction":"👍","reactions":[{"emoji":"👍","count":2}]}}
```

Для снятой реакции `myReaction: ""`; реакции с count=0 можно не включать. Те же `myReaction` и `reactions` возвращать у сообщения в `/internal-chat/messages/list`. Ошибка не должна отвечать success:true без подтверждённой записи.

Для обновления открытой истории других сотрудников можно вернуть в существующем `/notifications/poll` лёгкое событие, если запрошен тип `message_reaction_changed`:

```json
{"eventId":"EVENT_GUID","type":"message_reaction_changed","groupRef":"GROUP_GUID","messageRef":"MESSAGE_GUID"}
```

Это обновление истории без увеличения счётчика непрочитанных сообщений и без отдельного Push. Приложение перечитывает лёгкую историю только совпадающего открытого внутреннего чата. При повторном открытии актуальные реакции всегда берутся из messages/list.

## Даты клиентских чатов

В существующем `/clients/topics/list` вернуть `topicRef`, `createdAt` (создание переписки), `lastMessageAt` (последнее сообщение), существующие lastMessage/unreadCount. Даты — реальные ISO 8601 с часовым поясом. Отметка чтения, изменение названия или выключение уведомлений не должны менять lastMessageAt. Новый чат без сообщений сортируется по createdAt. Если даты уже есть, новых методов не требуется.

## Выключение уведомлений — хранение в 1С не нужно

Настройки хранятся в I-MAX/Timeweb по сотруднику + контуру + источнику чата + ссылке. Сервер проверяет настройку до доставки FCM/Web Push; сообщения в 1С сохраняются как раньше. Существующие регистрации устройств, токены и внутренний секрет не меняются.

В Push обязательно однозначно передавать чат:

- Клиентский: `type: "new_messages"`, `topicRef: "CLIENT_TOPIC_GUID"`.
- Внутренний: `type: "internal_chat_message"`, `topicRef: "GROUP_GUID"`.

Использование одного и того же типа new_messages для обеих разновидностей без признака источника не позволяет безопасно различить их. Если существующая отправка соответствует этому контракту, доработка 1С для выключения уведомлений не нужна. События ЗН/назначений/завершения документов этим переключателем не отключаются.

## Приёмка в тестовой 1С

1. Два сотрудника и согласованная внутренняя переписка; метод не должен принимать сообщение из другого чата.
2. Отправить ответ текстом и файлом; повторить с прежними IDs после потери ответа; проверить одну запись/один файл и сохранённую ссылку.
3. Поставить реакцию, повторить, заменить, снять; подтвердить отсутствие двойных счётчиков.
4. Повторно открыть чат под обоими сотрудниками; проверить оригинальных авторов, цитаты, суммарные реакции и персональный myReaction.
5. Проверить 401/403/422, удалённое сообщение, одинаковые ID в разных базах и одновременные запросы.
6. Выключить один чат в I-MAX; обычные Push других чатов и события ЗН должны поступать. Проверить Android и Web отдельно.

Никакие изменения боевой 1С этим документом автоматически не разрешаются. Сначала реализация/приёмка в тесте.
