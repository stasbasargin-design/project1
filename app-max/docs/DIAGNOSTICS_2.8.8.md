# I-MAX 2.8.8: панель администратора

Панель доступна по `/p/max-service/diagnostics/` рабочего сайта и `/diagnostics/` тестового. Вход — отдельные логин и пароль администратора через HTTPS. MAX ID, роль в интерфейсе и токен устройства не дают доступа к панели. Пароль хранится на сервере только как scrypt-хеш; реквизиты владельцу передаются отдельно, вне репозитория и APK.

## Что отображается

- Сотрудник и MAX ID из успешного ответа существующего `/auth/max`.
- Отдельные установки Android и Web/PWA, выбранный контур, версия и SHA сборки.
- Последний контакт приложения, последний подтверждённый ответ 1С, длительность, HTTP и безопасный код ошибки.
- Число ожидающих и ошибочных операций очереди, история последних 50 технических событий устройства, копирование отчёта.
- Агрегаты запросов прокси за час. HTTP 200 с `success:false` учитывается отдельно от HTTP 5xx.

Фильтры: сотрудник/MAX ID, контур, платформа, статус. По умолчанию выбрана боевая 1С. Время отображается в Екатеринбурге, UTC+5.

## Значение статусов и ограничения

«Нет свежих данных» после двух минут не означает, что 1С недоступна: приложение могло быть закрыто или устройство уснуло. «В фоне» показывается отдельно. «Ошибка операции» означает неуспешный последний запрос, «Сетевой сбой» — отсутствие HTTP-ответа, «Ошибка приложения» — блокирующее состояние интерфейса. Это мониторинг, а не исправление исходной сетевой проблемы.

Клиент передаёт небольшой отчёт каждые 30 секунд, пока видим, и при технических событиях. После потери сети до 50 событий остаются локально и передаются позже с прежними ID. История до обновления не восстанавливается. Устройства появляются после входа в новую версию; старые APK не передают отчёты. Установка — случайный ID профиля приложения, не аппаратный идентификатор телефона. Очистка данных/переустановка создаст новое устройство.

В отчёты не входят сообщения, фотографии, имена файлов, URL вложений, тела запросов, сырые сообщения ошибок/стек, токены и IP. Имя сотрудника и MAX ID доступны только администратору. Браузер/ОС/версия сообщаются клиентом; личность и контур задаёт сервер. Неактивные записи удаляются через 30 дней, предел — 2000 установок на сервис.

## Изоляция и отказоустойчивость

После успешной авторизации сервер добавляет необязательный заголовок `X-ITUS-Diagnostics-Token`. Он разрешает только запись диагностики этого сотрудника в выбранном контуре. Подпись проверяется сервером; токен не открывает панель и не выполняет операции 1С. Клиент не добавляет диагностический заголовок в обычные запросы 1С. Никаких дополнительных кодов подключения для сотрудников нет.

`POST /api/diagnostics/events` расположен вне прокси 1С; контурный путь — `/contours/production/api/diagnostics/events`. Ограничены размер, частота и параллелизм. Ошибки сборщика подавляются, повторяются с задержкой и не влияют на бизнес-запросы. Заголовок разрешён только для своего маршрута сбора, а ответный заголовок авторизации открыт штатным Android CORS.

Администратор читает `/diagnostics/api/devices` и `/diagnostics/api/devices/<opaque-id>` после HTTP Basic проверки, с `no-store`, ограничением попыток и CSP. Данные хранятся вне каталога приложения. Отдельная случайная подпись сбора и отдельное хранилище у test/production. Секреты отсутствуют в web-dist/APK. Без серверной конфигурации панель закрыта, приложение работает по прежнему пути.

Новые настройки сервера:

```ini
DIAGNOSTICS_STATE_DIR=/var/lib/itus-max-diagnostics
DIAGNOSTICS_ADMIN_USER=<отдельный администратор>
DIAGNOSTICS_ADMIN_PASSWORD_HASH=<scrypt-хеш>
DIAGNOSTICS_INGEST_SECRET=<случайный секрет, минимум 32 символа>
```

Закрытый env-файл подключается отдельным systemd drop-in с соответствующим `StateDirectory`. Для теста используются отдельные пути. Deploy должен копировать `diagnostics-server.mjs` вместе с серверными модулями. Существующие секреты, настройки 1С, Push, API, очереди и Android-подпись не меняются.

## Проверки и выпуск

Автоматические проверки используют вымышленного сотрудника и локальный HTTP-сервис: защищённый доступ, подмена токена/личности/контура, потеря подтверждения и дедупликация, сохранение после перезапуска, отсутствие приватных полей, ограничение тела, неизменность больших ответов 1С, CORS, offline и смена пользователя, ошибка localStorage, настоящий браузер, фильтры, защита от HTML-инъекции и мобильный экран.

Перед production выполняются полный `npm ci`, `npm test`, `npm run test:review`, `npm run build`, проверка diff и установка точного CI-пакета на max-test с резервной копией. Живая проверка авторизации и своего технического отчёта не изменяет документы/чаты и не отправляет Push сотрудникам. После неё — штатный PR/deploy и подписанный совместимый APK. Результаты и точные SHA фиксируются в отчёте выпуска.

Физическое Android-устройство не подменяется автоматическим браузерным тестом. Нужна последующая пользовательская проверка установки и появления устройства в панели.

## 1С и откат

Изменения в 1С **не требуются**. Существующие методы, тела запросов, завершение документов, отправка файлов и Push-контракты сохраняются.

Откат сервиса: остановить только нужную службу, сохранить неудачный каталог под отдельным именем, вернуть предыдущий каталог атомарным переименованием и запустить службу. Восстановить предыдущий deploy-скрипт, если он менялся. Отдельное диагностическое хранилище и существующие очереди не удалять. Старый код игнорирует новый env/drop-in; их можно оставить до разбора. Для APK сохраняются прежний пакет и сертификат; установка Android с понижением versionCode не предлагается.
