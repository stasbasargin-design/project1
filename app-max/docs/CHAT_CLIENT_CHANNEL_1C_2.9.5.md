# Контракт 1С: клиентские ответы и настоящие реакции, 2.9.5

Требование владельца: клиент видит ответ и настоящую реакцию в своём MAX/Telegram. Замена реакции эмодзи-сообщением запрещена.
Секреты ботов, внешние chat/message ID и вызовы Bot API остаются в 1С/серверной интеграции. В приложение их передавать не нужно.

## Объявление поддержки

В существующем `/auth/max`, в том же блоке данных, что и текущие capabilities:

```json
{"chatCapabilities":{"internal":{"replies":true,"reactions":true},"clients":{"replies":true,"reactions":true}}}
```

В каждой теме `/clients/topics/list` можно вернуть `chatCapabilities:{"replies":true,"reactions":false}`. Тема может запретить объявленное общее действие; без общего флага действие не включается. Если блок темы присутствует, оба поля передаются явно.
`reactions:true` означает поддержку настоящей реакции именно этим ботом/каналом, включая её замену и снятие. Не объявлять флаг по наличию одного внутреннего метода без внешней доставки. Для MAX требуется подтверждённый работающий API интеграции.

## Ответ на сообщение клиента

В существующих POST `/clients/messages/send` и `/clients/files/send` дополнительно принять `replyToMessageRef` — стабильную ссылку сообщения из текущей темы. Остальные поля, маршруты, `clientMessageId` и `requestId` сохраняются. Для нескольких файлов ссылка ответа сохраняется у каждой части.
Проверить доступ сотрудника и принадлежность исходного сообщения этой теме/контуру. По сохранённому соответствию найти внешний идентификатор сообщения. Telegram: штатный `reply_parameters`; MAX: штатный `link` типа `reply`. Если источник удалён или канал не поддерживает ответ — вернуть понятную ошибку, не отправлять молча обычное сообщение.

В `/clients/messages/list` возвращать:

```json
{"messageRef":"REPLY_REF","text":"Ответ","replyToMessageRef":"ORIGINAL_REF","replyTo":{"messageRef":"ORIGINAL_REF","authorName":"Автор","text":"Исходный текст","fileName":"photo.jpg"}}
```

Автор — фактический сохранённый отправитель, не текущий читатель. Недоступный исходник не должен раскрывать чужой текст.

## Реакция клиента

Новый POST `/clients/messages/react`:

```json
{"topicRef":"TOPIC_REF","topicId":"TOPIC_REF","messageRef":"MESSAGE_REF","emoji":"👍","requestId":"UUID"}
```

Стандартные auth/context-поля приложение добавляет прежним способом. `emoji` — желаемое конечное состояние; пустая строка снимает реакцию. Это не команда «переключить». Допустимые эмодзи: 👍 ❤️ 😂 😮 😢 🙏 ✅ 👎; неподдерживаемый каналом эмодзи отклоняется явно. Проверить доступ, тему и внешнее сообщение.

Только после успешной настоящей реакции в канале вернуть:

```json
{"success":true,"data":{"messageRef":"MESSAGE_REF","myReaction":"👍","reactions":[{"emoji":"👍","count":1}],"delivery":{"status":"sent","kind":"native-reaction"}}}
```

Если операция принята фоновой интеграцией: `delivery.status="queued"`. Приложение показывает ожидание, не рисует подтверждённую реакцию. После доставки обновить историю и событие `/notifications/poll` типа `client_message_reaction_changed` с `topicRef` и `messageRef`. Повтор запроса с тем же requestId возвращает состояние первоначальной операции. Сохранять журнал операции и внешнего результата, не дублировать вызов после потерянного ответа.

`/clients/messages/list` возвращает `reactions` и `myReaction` текущего сотрудника; числовые счётчики не увеличиваются от повторов. Telegram-бот имеет ограничение на число собственных реакций: несколько сотрудников не становятся несколькими отдельными внешними пользователями. Согласовать общее состояние реакции бота, сериализовать изменения одного внешнего сообщения и корректно отражать эту модель внутри I-MAX.

Если невозможно подтвердить настоящую реакцию MAX — вернуть `reactions:false` для соответствующей темы. Не отправлять эмодзи текстом, не отмечать внутреннюю реакцию как доставленную клиенту.

## Пересылка

Новых методов для пересылки нет. Выбранные записи создают обычные сообщения через существующие `/clients/messages/send`, `/clients/files/send`, `/internal-chat/messages/send`, `/internal-chat/files/send`. Копируются только выбранные текст/байты файла, с новыми стабильными идентификаторами получателя. Документ дефектовки не меняется.
Для чтения исходного файла используются существующие `/defects/start` либо `/clients/messages/list` / `/internal-chat/messages/list` с точными ссылками сообщения и вложения. Проверки доступа сохраняются.

## Приёмка с 1С

1. Ответ на текст и файл доходит клиенту с правильной исходной цитатой.
2. Установка/замена/снятие настоящей реакции видны в канале, а не в виде нового текстового сообщения.
3. Потеря ответа и повтор с прежним requestId не создают дубль.
4. Очередь внешней доставки не выдаётся за успешную доставку.
5. Чужая тема, другой контур и отсутствующий внешний message ID отклоняются.
6. У нескольких сотрудников одинаковое общее состояние; myReaction определяется по действующему сотруднику.

Справка: https://core.telegram.org/bots/api#setmessagereaction и https://dev.max.ru/docs-api/methods/POST/messages. Наличие MAX-ответов не подтверждает наличие API реакций; последнее требуется отдельно проверить интегратору.
