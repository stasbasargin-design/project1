# I-MAX 2.9.8: текстовые коды внутренних реакций

Этот контракт заменяет Unicode-формат реакций из ТЗ 2.9.6.
Область: только реакции во внутренних группах и личных чатах сотрудников.
Обычные сообщения, смайлы внутри их текста, ответы, файлы, клиентские чаты,
MAX/Telegram, очереди и завершение документов не меняются.

## 1. Готовность в /auth/max

В успешном ответе `POST /auth/max`, внутри `data`:

```json
{
  "chatCapabilities": {
    "internal": {
      "replies": true,
      "reactions": true,
      "reactionEncoding": "code-v1"
    }
  }
}
```

Сохранить user, availableTabs и остальные поля. `replies` включать только при
реализованных ответах; это независимая возможность. Значения replies/reactions —
boolean, reactionEncoding — строка с точным значением code-v1.

Важная совместимость: в существующем JSON-запросе уже передаётся
`version: "i-max-2.9.8"`. Для старых клиентов 2.9.7 и ниже (а также неизвестной
версии) возвращать `reactions:false`, если 1С больше не поддерживает Unicode.
Старый APK не понимает reactionEncoding и при reactions:true отправит старый emoji.
Для версии 2.9.8 и следующих поддерживаемых версий включать реакции только когда
метод ниже реализован и сотрудник имеет право на это действие.

Новый I-MAX не отправляет реакцию, если не получены одновременно reactions:true
и reactionEncoding:"code-v1". Обычные чаты и независимые ответы продолжают работать.
После публикации /auth/max пользователь повторно авторизуется.

### Защита старых версий

Использовать существующее верхнеуровневое поле запроса `version`, а не
User-Agent, имя файла APK или MAX ID. Для `i-max-2.9.7` и более ранних версий,
отсутствующего, пустого или нераспознанного значения возвращать в успешном ответе:

```json
{"chatCapabilities":{"internal":{"reactions":false}}}
```

Это фрагмент ответа: user, availableTabs, internal.replies и остальные поля
сохраняются. Вход не блокировать; отключается только неподдерживаемая возможность
реакций. Для поддерживаемой 2.9.8 вернуть reactions:true и reactionEncoding:code-v1.
Будущие версии включать по явно поддерживаемому формату; номера сравнивать как
три целых компонента major/minor/patch, не как строку или дробное число.

Проверка должна быть и в `/internal-chat/messages/react`: старый клиент мог
сохранить ранее выданный reactions:true. Если версия не поддерживает code-v1
или вместо emojiCode передано прежнее поле emoji, вернуть HTTP 422 без записи:

```json
{"success":false,"error":{"code":"REACTION_CLIENT_UPDATE_REQUIRED","message":"Для реакций обновите I-MAX до версии 2.9.8 или новее"}}
```

Не изменять счётчики, сообщение или чужую реакцию при отказе. Штатные проверки
авторизации и прав сохраняются; version служит совместимости и не заменяет их.
Неизвестный emojiCode поддерживаемого клиента также отклонять без записи.
Обычные тексты, файлы, ответы и просмотр чатов старых клиентов продолжают работать.

Проверить /auth/max для 2.9.8, 2.9.7, более старой версии и запроса без version;
затем повторить старый запрос react с ранее закешированным разрешением и
убедиться в отсутствии изменений. Для 2.9.8 сохранить успешные set/replace/clear
и повторную загрузку истории.

## 2. Справочник кодов

| Код в 1С | Отображение I-MAX |
|---|---|
| thumbs_up | 👍 |
| heart | ❤️ |
| laugh | 😂 |
| wow | 😮 |
| sad | 😢 |
| thanks | 🙏 |
| check | ✅ |
| thumbs_down | 👎 |
| пустая строка | снять свою реакцию |

В запросе и хранении использовать только коды. Не заменять весь текст сообщения
и не пытаться кодировать Unicode-последовательностями JSON: данная схема — отдельное
поле emojiCode, а не экранирование поля emoji. Неизвестные коды отклонять с 422.

## 3. POST /internal-chat/messages/react

Существующий маршрут; изменяется формат реакции. Общие MAX/auth-поля сохраняются.

```json
{
  "groupRef": "GROUP_GUID",
  "groupId": "GROUP_GUID",
  "messageRef": "MESSAGE_GUID",
  "emojiCode": "thumbs_up",
  "requestId": "REQUEST_UUID"
}
```

`emoji` с настоящим смайлом новый клиент не отправляет. `groupRef` и `groupId`
обозначают одну существующую переписку, messageRef — сохранённое сообщение в ней.
Сотрудника определять по штатному авторизованному MAX-контексту, не по полям автора.
Проверять права, принадлежность сообщения чату и текущему контуру.

Правила записи:

- Одна текущая реакция сотрудника на сообщение в своём контуре.
- Тот же код ничего не добавляет и не увеличивает счётчик.
- Другой код заменяет предыдущий.
- Пустая строка удаляет только реакцию текущего сотрудника.
- Это установка конечного состояния, не переключатель toggle.
- Запись, счётчики и результат requestId — атомарно. Повтор requestId возвращает
  первоначальный результат без повторного изменения счётчиков.
- HTTP 200 / success:true возвращать только после подтверждённого сохранения.

## 4. Подтверждение и история

Успешный ответ:

```json
{
  "success": true,
  "data": {
    "messageRef": "MESSAGE_GUID",
    "myReactionCode": "thumbs_up",
    "reactions": [
      {"emojiCode": "thumbs_up", "count": 2},
      {"emojiCode": "heart", "count": 1}
    ]
  }
}
```

`myReactionCode` — реакция текущего сотрудника, общие reactions — счётчики всех
сотрудников. Для снятия вернуть myReactionCode:"", сохранив реакции других.
Для каждого кода — одна строка, count — положительное целое JSON-число.
Строки с нулём не возвращать. При установленной реакции её код должен быть
в общих счётчиках. Не возвращать Unicode-поля emoji и myReaction в новом контракте.

В существующем `/internal-chat/messages/list` добавить те же myReactionCode и
reactions к каждому сообщению. Это нужно для повторного открытия, других устройств
и правильного определения своей реакции под другим сотрудником.

После изменения через существующий `/notifications/poll` можно вернуть:

```json
{
  "eventId": "EVENT_UUID",
  "type": "message_reaction_changed",
  "groupRef": "GROUP_GUID",
  "messageRef": "MESSAGE_GUID"
}
```

Событие перечитывает историю. Эмодзи в событии не нужен; новые сообщения,
непрочитанные и отдельную отправку Push ради реакции не создавать.

## 5. Приёмка

1. Проверить старый APK: reactions:false, обычные сообщения работают.
2. Войти в 2.9.8; подтвердить code-v1 из /auth/max.
3. Поставить, повторить, заменить и снять реакцию; в запросах только emojiCode.
4. Повторить запрос с прежним requestId: счётчики не меняются повторно.
5. Открыть историю под сотрудниками А и Б: общие счётчики одинаковы, myReactionCode
   соответствует каждому сотруднику.
6. Закрыть/открыть чат: смайлы восстановились из кодов.
7. Проверить ошибку/неподтверждённый ответ: I-MAX не показывает реакцию сохранённой.
8. Чужой чат/контур и неизвестный код отклоняются без записи.
9. Клиентские ответы и реакции не включаются; пересылка и файлы сохранены.
