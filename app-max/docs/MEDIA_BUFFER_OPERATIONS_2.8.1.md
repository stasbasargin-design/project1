# I-MAX 2.8.1 — эксплуатация

База: GitHub main `f22ae1a9ea5e17ef663c3b8eb1202ba136742cef`, версия 2.8.0.
Ветка кандидата: `fix/2.8.1-stable-submissions`. Android: `ru.eazia.imax`,
versionName 2.8.1, versionCode 2801. Подпись должна совпасть с установленной
2.8.0; новый keystore не создаётся.

## Исправления клиента

- Блокировки действий снимаются после успеха/ошибки, в том числе после замены DOM.
- Сообщения не ждут завершения файловой очереди; сами файлы идут последовательно.
- Готовые формы контрольного листа и качества перерисовываются после снятия busy.
- Ответы старого окна постов/исполнителей/истории не меняют окно другого ЗН.
- Дефектовка обновляет историю при повторном открытии; локальный Blob не теряется.
- Сохранённый конверт операции не меняется после повторного входа.
- Web Locks вместе с атомарной блокировкой IndexedDB предотвращают второй sender.
  После закрытия вкладки Web Lock освобождается браузером: новое окно может
  восстановить старую операцию сразу, не ожидая прежнего десятиминутного lease.
  Без Web Locks резервный lease составляет 90 секунд с продлением.
- Фоновая ошибка не подменяет открытую форму; отчёт доступен в очереди.
- Большие ответы не клонируются для поиска bot ID; Node проксирует чтение потоком.

## Серверная конфигурация

Файлы секретов находятся вне Git и каталога приложения, root:root 600.
Переменные: `MEDIA_BUFFER_ENABLED=true`, `MEDIA_STATE_DIR`, `MEDIA_CONTEXT`
(`test`/`production`), `MEDIA_S3_BUCKET`, `MEDIA_S3_ACCESS_KEY`,
`MEDIA_S3_SECRET_KEY`, `MEDIA_S3_ENDPOINT=https://s3.twcstorage.ru`,
`MEDIA_S3_REGION=ru-1`, `MEDIA_UPLOAD_MODE=relay`.

`MEDIA_CONTEXT` обозначает размещение приложения, а не выбор боевой базы 1С.
Обе существующие публикации в рамках этой задачи остаются на `aa6_ea_test9`.

Для тестовой службы используется `/etc/itus-max-s3-test.env` и отдельный
`StateDirectory=itus-max-media-test` с правами 700. Основная служба должна иметь
свой отдельный журнал/файл env; записи и устройства между доменами не копируются.

По умолчанию используются двоичные части через HTTPS Node → S3: ключ выделенного
пользователя разрешает объекты, но не изменение CORS бакета. Полный файл не
буферизуется в RAM и не передаётся в 1С на этом этапе. Режим `direct` можно
включить после настройки CORS только для адресов I-MAX. Бакет остаётся приватным.

Журнал заданий хранится отдельно от приложения. Запись заменяется атомарно и
синхронизируется на диск; после перезапуска восстанавливаются исходные IDs.
Квитанция 1С записывается до ответа клиенту. Один обработчик импортирует файлы;
чтение, вход, сообщения и проверки состояния работают независимо.

В S3 используется только префикс `imax-buffer/`. Другие объекты не удаляются.
Подтверждённый буфер удаляется через 24 часа. Незавершённая загрузка частями
прерывается после 48 часов бездействия; исходник остаётся в IndexedDB и может
быть загружен повторно с прежними деловыми IDs. Ошибки/неоднозначные результаты
не очищаются автоматически. По умолчанию бюджет буфера 50 ГиБ, максимум 50
незавершённых заданий сотрудника / 500 на контур. Эти пределы — защита ёмкости,
а не прежний лимит отдельного видео. Они изменяются серверными настройками.

## Подключение устройства

Администратор от имени службы выполняет `scripts/media-device-code.mjs MAX_ID`
с правильным `MEDIA_STATE_DIR`. Код действует 15 минут, используется один раз
и передаётся сотруднику защищённым рабочим каналом. Пользователь вводит его в
«Настройки → Крупные файлы». Устройство запоминается на 30 дней; отключить его
можно там же. Коды и токены не добавлять в отчёты, Git и общие инструкции.

## Совместимость и откат

IndexedDB `itus-operation-queue`, store `operations`, версия **4**. Записи v2/v3
сохраняются без изменения тел/IDs и старого транспорта. Повышение версии
блокирует старые отправители, которые не понимают S3-маршрут. Перед обновлением
веб-версии нужно закрыть старые вкладки. Очищать IndexedDB нельзя.

Серверный выпуск идёт из точного GitHub SHA через `scripts/deploy-test.sh`
на max-test; основной сайт — через существующий deploy workflow и обновлённый
`scripts/deploy-max.sh`, копирующий все серверные модули.

Перед переключением создаётся резервная копия приложения. Secret env и журнал
заданий не находятся внутри переключаемого каталога. При ошибке health/SHA
восстанавливается предыдущий каталог. Откат не удаляет журнал и буфер S3.
Старый клиент v3 не должен отправлять новые S3-пакеты напрямую; схема v4
останавливает такой запуск. Для продолжения новой очереди нужна версия 2.8.1.

## Приёмка

Автоматические проверки: кнопки после ошибки/замены DOM, два сообщения,
повторное открытие дефектовки, смена ЗН с задержанным ответом, два sender,
потеря ответа, пять попыток, 422/409, изоляция владельцев, смешанный пакет,
один complete, HTTP Range и точное совпадение файла. Есть реальные браузерные
проверки; отдельные проверки S3 выполняются собственным синтетическим объектом.

Обязательно фиксировать отдельно фактический результат тестовой 1С и проверки
физических Android/iPhone. Прохождение локальных тестов не означает, что они
выполнены. Полностью закрытое iOS/PWA не гарантирует загрузку локального файла:
автономно продолжается только уже принятый S3-буфер.
