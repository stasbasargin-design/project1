# I-MAX 2.8.0

База: GitHub main / production 2.7.13, `22e37e2a4b50d2788ad4a97c429d942a859f4bc3`.
Ветка: `feature/2.8.0-media-layout`. Android versionCode: 2800, пакет `ru.eazia.imax`.
Владелец разрешил реализацию и выпуск новой версии в этой задаче; отдельно подтвердил,
что после завершения приёмки кнопка должна быть неактивной.

## Пользовательские изменения

- Видео без прежнего порога 15 МиБ во всех маршрутах отправки, включая выбор как обычного файла.
  Бинарная локальная очередь и потоковое преобразование на Node; контракт 1С сохранён.
- Неактивная кнопка завершённой приёмки, сохранение известного статуса на устройстве.
- Действие добавления дефекта в МП независимо от открытой формы приёмки.
- Статус акта и точка справа снизу в карточке ЗН: зелёная/красная/серая по достоверным данным.
- Зафиксированная навигация обычных экранов; в чатах сохраняется собственная неподвижная оболочка.
- Меню и история обслуживания ограничены экраном, содержимое прокручивается внутри.
- Настройки → «Размер текста и блоков»: компактный, обычный, крупный, очень крупный.
  Настройка локальная, без изменения данных 1С.

## Проверка

`npm ci`, полный `npm test` (28 наборов), `npm run test:review`, `npm run build`.
В реальном браузере проверены ширины 360/393/800/1200, landscape, клавиатура,
safe-area, меню/история и четыре масштаба; снимки сохранены отдельно в материалах выпуска.
Синтетическое видео >40 МиБ проходит все три серверных маршрута с побайтным совпадением.
Проверены неправильный маршрут, неполная передача, уборка временного файла и стабильные ID.
В IndexedDB проверены сохранение Blob после повторного открытия и сохранность старых записей.

Физические устройства и реальная запись больших видео в 1С не выдаются за проверенные.
Точные SHA, GitHub Actions и контрольная сумма APK фиксируются в GitHub Release после сборки.

## Очередь и совместимость

База `itus-operation-queue`, store `operations` сохранены; версия схемы становится **3**.
Записи не удаляются. Это защищает Blob от старого JSON-only отправителя, который иначе
мог бы превратить бинарное содержимое в пустой объект.

Если открыта старая вкладка, обновление базы может быть заблокировано. Приложение просит
закрыть старые вкладки и повторить сохранение; выбранные файлы остаются в форме.
Старый APK/старый веб-клиент после миграции не сможет обрабатывать очередь версии 3.
Не очищать данные приложения и IndexedDB. Полностью закрытый браузер не гарантирует
фоновое исполнение: отправка возобновляется после открытия и входа владельца.

## Установка Android

GitHub Actions собирает unsigned release; подписать локально существующим совместимым
ключом `906BA322884FCA8C92C2D884CDEBB8EC8F4EB3D527BAF7D06929970BA77BCB47`.
Имя готового файла: `I-MAX-2.8.0.apk`. Закрытый ключ не передаётся в GitHub.
Совместимость с другими историческими сертификатами не заявляется; удалять рабочее
приложение с неотправленными данными нельзя.

Установка APK с сайта/из файла требует разрешения Android на установку из данного
источника. Приложение не может выключить это системное предупреждение. Play Protect
также может проверить новую сборку; «предупреждение исчезнет» не гарантируется.
Для штатного распространения через магазин нужны аккаунт издателя, проверка и согласованная
схема подписи/обновления. В этом выпуске публикация в Google Play/RuStore не выполняется.

Официальные источники:
- https://developer.android.com/distribute/marketing-tools/alternative-distribution
- https://support.google.com/android/answer/2812853

## Deployment и откат

Сначала сверить GitHub main и production, затем штатный PR → main → GitHub Actions.
Новый deploy-скрипт копирует `media-proxy.mjs`; до merge установить проверенную версию
`app-max/scripts/deploy-max.sh` в `/usr/local/bin/deploy-max.sh` с отдельной резервной копией.

Workflow создаёт резервную копию приложения и `/etc/nginx/snippets/itus-max.conf`.
Только в I-MAX location снимается прежний `client_max_body_size 32m`, отключается
`proxy_request_buffering`, таймауты чтения/передачи становятся 1200s. Node оставляет
прежний предел для обычного JSON и принимает бинарный транспорт только на трёх маршрутах.
При неуспехе проверки применяется прежний каталог приложения и прежний Nginx snippet.
Секреты, 1С URL, Firebase, VAPID и остальные сайты не меняются.

После выпуска сверить health/build-info SHA, файлы, рабочий Push config, подпись/API APK.
Ручной откат: использовать только подтверждённые каталоги backup/previous из успешного
Actions run; вернуть сохранённый Nginx snippet, выполнить nginx -t/reload. Очереди на
устройствах не очищать. Для схемы 3 потребуется совместимый клиент 2.8.0 или новее.
