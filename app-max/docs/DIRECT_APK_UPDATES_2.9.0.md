# I-MAX 2.9.0: обновление Android с Timeweb

База: production 2.8.9, `f93a595b5e6a98dd02669a7f1843a3e7e7b7cdc9`.
Ветка: `feature/direct-apk-updates-290`. Новая версия: 2.9.0 / versionCode 2900.

## Область

Проверка новой Android-версии после входа и при возврате в приложение (не чаще одного раза в 6 часов после успешной проверки), ручная кнопка в настройках. APK скачивается по HTTPS напрямую с нашего сервера. Пользователь открывает системную установку самостоятельно. Новое разрешение `REQUEST_INSTALL_PACKAGES` используется только для обновления своего пакета. Обход системной защиты не предусмотрен.

Для bootstrap нужно один раз установить 2.9.0 обычным способом. В 2.8.9 этого нативного механизма нет. Для последующих версий публикация состоит из штатного выпуска кода, подписания APK прежним ключом, проверки и атомарного обновления метаданных на Timeweb. Публикация web-кода сама по себе не публикует APK.

Сохраняются applicationId `ru.eazia.imax`, прежняя совместимая подпись, WebView origin, имена/версии IndexedDB и localStorage. Не изменяются API 1С и адреса контуров, чаты, авторы сообщений, Push, маршруты документов, IDs/lease/повторы очереди, сжатие, S3 и зависимости. **Разработчику 1С изменений делать не нужно.**

## Защита файлов и документов

Проверка обновлений и скачивание не обращаются к 1С. При установке проверяются SHA256/размер APK, фактический package/versionCode и совпадение сертификата с установленным приложением. Адреса зафиксированы в native policy; JS не может передать произвольный URL, путь или команду. Redirect запрещён, TLS проверяется штатно. APK находится в приватном cache приложения и передаётся только системному установщику через FileProvider.

Открытие установщика блокируется при активном HTTP-запросе, фоновой отправке/операции, pending/sending-пакете текущего сотрудника/контура, открытой форме или непустом черновике чата. Очередь не очищается, не «досылается» установщиком и не переигрывается. Консервативная блокировка предлагает закончить отправку и закрыть редактор. Скачивание можно свернуть, продолжая работу в приложении.

Внутреннее ограничение скачивания APK 256 МиБ и 5 минут относится только к бинарному установщику, не к фото/видео приложения. На Android остаются системное разрешение источника, подтверждение установки и возможная проверка Play Protect/разблокировка телефона.

## Timeweb

Маршруты, вне 1С и контурных API:

- `GET/HEAD /p/max-service/updates/android/latest.json`;
- `GET/HEAD /p/max-service/updates/android/I-MAX-<version>.apk`.

Хранилище по умолчанию `/opt/itus-max-updates`; на службе с `WEB_PUSH_CONTEXT=test` — `/opt/itus-max-updates-test`. Для отдельной установки доступен несекретный `APP_UPDATES_DIR`. Секретные env и Nginx менять не требуется. Владелец каталога root, каталог 755, файлы 644: служба читает, не записывает. APK/manifest вне каталога приложения, переживают deploy. Закрытого HTTP upload/admin endpoint нет.

`latest.json`: `enabled`, `schema:1`, `packageName`, `version`, `versionCode`, `fileName`, `bytes`, `sha256`, `signerSha256`, `commit`, `minSdk:24`, массив `notes` (до 8 пунктов по 400 символов). Все digest — lowercase hex. Маршрут APK ограничен именем текущего опубликованного файла; symlink/неполный файл/неверный manifest не обслуживаются. Нет manifest — `{ "enabled": false }`. Отказ обновлений не влияет на health и API 1С.

Сначала выгрузить APK под временным именем, проверить его SHA256/подпись/package/version, атомарно переименовать в окончательный APK. Затем атомарно заменить `latest.json`. Для первой публикации не выбирать более высокий versionCode из непроверенной сборки. Не хранить keystore или пароли на публичном сервере. Для отзыва предложения атомарно записать `{ "enabled": false }` — уже установленные версии не понижаются.

## Проверки и выпуск

`npm ci`, весь `npm test`, review/build, git diff --check. Отдельно: серверный HTTP-контракт subpath/HEAD/повреждённая публикация/path traversal; JVM-политика URL/package/hash; браузерная интеграция вход → предложение → скачивание в фоне → запрет установки при активном файле и черновике → запрос системного разрешения. Только синтетические документы/переписка. Нативный код компилируется в штатном Android CI. Не объявлять проверенной физическую установку/системный диалог без реального устройства.

Тестовый web-пакет и unsigned APK формируются одним workflow из одного SHA. После тестового deployment сравнить публичные файлы с manifest артефакта и сохранить старые каталог/commit. В тестовом каталоге обновлений проверить disabled, валидный APK download/HEAD/хэш и отказ повреждённых метаданных, не публикуя предложение в production.

Production только штатным PR-процессом после требуемого владельцем подтверждения точного SHA. APK подписывается локально историческим совместимым ключом; закрытый ключ не попадает в CI. Перед передачей сверить сертификат с 2.8.9, package `ru.eazia.imax`, versionCode 2900, production API, Firebase, build-info и новые updater classes.

## Откат

1. Отозвать предложение обновления: атомарный `latest.json` с `enabled:false`, сохранив прежние файлы для аудита.
2. Для web/server восстановить сохранённый application-каталог только нужной службы штатным rollback; env, очереди, media-state и сертификаты не трогать.
3. Уже установленный Android APK не откатывать APK с меньшим versionCode: исправление выпускается новой совместимой версией. Не удалять приложение и не очищать его данные.
