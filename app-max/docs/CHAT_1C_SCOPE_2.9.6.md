# ТЗ 1С: уточнённый состав I-MAX 2.9.6

> Для 2.9.8 раздел про реакции и их объявление заменён на `REACTION_CODES_1C_2.9.8.md`: только ASCII-коды, с явным `reactionEncoding: "code-v1"`. Остальные разделы сохраняются.

Заменяет ранее переданное ТЗ 2.9.5 по клиентским ответам и реакциям.
По решению владельца ответы с цитатой и реакции реализуются только во внутренних чатах сотрудников I-MAX. Внешние клиентские чаты MAX/Telegram сохраняют обычные сообщения/файлы и пересылку из них и в них.

## Что не нужно делать для внешнего чата

- Не добавлять `/clients/messages/react`.
- Не добавлять поддержку `replyToMessageRef` в `/clients/messages/send` и `/clients/files/send` ради этого выпуска.
- Не подключать Bot API ответов/реакций MAX/Telegram и не отправлять эмодзи вместо реакции.
- Не добавлять клиентские capabilities или событие `client_message_reaction_changed`.

## Объявление внутренних возможностей

В существующем ответе `POST /auth/max`, внутри data, вернуть:

```json
{"chatCapabilities":{"internal":{"replies":true,"reactions":true}}}
```

Если data — массив блоков, добавить отдельный блок chatCapabilities, не заменяя остальные. Значения — boolean; включать только реализованную функцию. Роли/вкладки/авторизацию не менять. После публикации обработчика пользователь повторно входит в I-MAX.

## Внутренний ответ

В существующих `POST /internal-chat/messages/send` и `POST /internal-chat/files/send` поддержать необязательный `replyToMessageRef` — стабильную ссылку сообщения текущей группы/личной переписки.

```json
{"groupRef":"GROUP_GUID","groupId":"GROUP_GUID","clientMessageId":"STABLE_UUID","requestId":"REQUEST_UUID","text":"Ответ сотрудника","replyToMessageRef":"ORIGINAL_MESSAGE_GUID"}
```

Для файла используются прежние kind/file с тем же дополнительным полем. Обычный запрос без поля работает по прежнему контракту. Проверять авторизацию, доступ к группе, принадлежность оригинала этому чату/контуру. Сохранять связь и текст/файл транзакционно. Повторы с прежними clientMessageId/requestId не создают дублей.

В ответе отправки и `/internal-chat/messages/list` возвращать:

```json
{"messageRef":"REPLY_GUID","authorName":"Автор ответа","text":"Ответ","replyToMessageRef":"ORIGINAL_MESSAGE_GUID","replyTo":{"messageRef":"ORIGINAL_MESSAGE_GUID","authorName":"Автор оригинала","text":"Исходный текст","fileName":"photo.jpg"}}
```

Авторы берутся из сохранённых отправителей, не из текущего читателя. Для удалённого/недоступного оригинала — безопасная заглушка. Полный файл для цитаты не нужен.

## Внутренняя реакция

`POST /internal-chat/messages/react`:

```json
{"groupRef":"GROUP_GUID","groupId":"GROUP_GUID","messageRef":"MESSAGE_GUID","emoji":"👍","requestId":"REQUEST_UUID"}
```

Стандартные auth-поля и X-ITUS-Request-Id передаются штатно. Установить точное конечное состояние: другой эмодзи заменяет прежний, пустая строка снимает. Повтор значения не переключает реакцию и не увеличивает счётчик. Одна реакция сотрудника на сообщение внутри контура. Допустимы 👍 ❤️ 😂 😮 😢 🙏 ✅ 👎 и пустая строка.

Успешный ответ:

```json
{"success":true,"data":{"messageRef":"MESSAGE_GUID","myReaction":"👍","reactions":[{"emoji":"👍","count":2}]}}
```

myReaction относится к текущему сотруднику, reactions — общие счётчики. Те же поля возвращать в истории. После записи можно передать существующим `/notifications/poll` событие:

```json
{"eventId":"EVENT_UUID","type":"message_reaction_changed","groupRef":"GROUP_GUID","messageRef":"MESSAGE_GUID"}
```

Событие перечитывает открытую историю. Отдельный Push и увеличение непрочитанных не нужны. Повтор requestId возвращает первоначальный результат; изменение транзакционно.

## Пересылка из внешнего чата и в него

Новых методов пересылки не требуется. Используются обычные существующие:

- `/clients/messages/send` и `/clients/files/send` — получатель клиентская тема, topicRef/topicId;
- `/internal-chat/messages/send` и `/internal-chat/files/send` — получатель внутренний чат, groupRef/groupId.

Передаются выбранные текст и байты файла с новыми стабильными clientMessageId/clientFileId/requestId для получателя. Повтор использует те же IDs. Исходный автор не подставляется в автора нового сообщения, исходные документы/переписка не меняются. У получателя — обычные сообщения, без полей цитирования и нативной отметки пересылки бота.

Для чтения выбранного файла используются действующие `/clients/messages/list`, `/internal-chat/messages/list` либо `/defects/start` с точными идентификаторами сообщения/записи и вложения. Существующий механизм доступа к содержимому сохранить. Если файл уже выдаётся штатно, менять его контракт не требуется.

## Приёмка

1. Внутренний ответ на текст/файл сохраняет правильную цитату после повторного открытия.
2. Реакция устанавливается/заменяется/снимается; два сотрудника видят общие счётчики и свой myReaction, без дублей при повторе.
3. Во внешнем чате нет действий ответа/реакции и запросов их API, даже при случайно переданных client capabilities.
4. Выбранные текст/фото/видео/документ пересылаются из внешнего во внутренний/другой внешний чат и обратно после выбора получателя и подтверждения.
5. Повторная попытка не создаёт дублей; автор нового сообщения — пересылающий сотрудник; старые сообщения/документы не меняются.
6. Обычные сообщения, вложения, авторизация, Push, контуры и очереди работают по прежней логике.
