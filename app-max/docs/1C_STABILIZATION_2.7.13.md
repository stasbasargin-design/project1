# I-MAX 2.7.13: что требуется от HTTP-сервиса 1С

Дата: 29.10.2026. Документ для разработчика 1С.

## Область релиза

Релиз исправляет клиентскую очередь, состояния кнопок, геометрию интерфейса,
Android Back, восстановление Push и ошибки QR. Приложение сохраняет существующие
маршруты и поля запросов. Новые HTTP-методы для установки 2.7.13 не требуются.

Основные изменения поведения:

- весь пакет сохраняется локально до первой отправки;
- одна операция сохраняет свои идентификаторы, тело, владельца и контур при повторе;
- после выхода очередь приостанавливается; другой сотрудник не отправляет её данные;
- переключение ЗН не меняет реквизиты уже сохранённой операции;
- завершение приёмки/дефектовки ждёт подтверждения обязательных частей;
- чаты сохраняют исходящие операции в ту же постоянную очередь;
- HTTP 422 не считается успехом и не повторяется автоматически;
- пользователь может получить безопасный технический отчёт и открыть сохранённую очередь после повторного входа.

Это не новое требование переписать конфигурацию. Ниже перечислены уже существующие
гарантии контракта, которые нужно подтвердить на опубликованном сервисе. Если они
выполнены, серверные доработки для этих исправлений не нужны.

## 1. Идемпотентность сохранения и завершения

Применить к следующим существующим методам:

| Маршрут | Что сохраняется при повторе |
|---|---|
| `/defects/entries/add` | `requestId`, `clientEntryId`, `documentRef`, тело записи/файла |
| `/acceptance/complete` | `requestId`, исходные `orderRef`, `documentRef`, значения формы |
| `/defects/complete` | `requestId`, исходные `orderRef`, `documentRef` и тело |
| `/clients/messages/send`, `/internal-chat/messages/send` | `requestId`, `clientMessageId`, контекст чата, текст |
| `/clients/files/send`, `/internal-chat/files/send` | `requestId`, `clientMessageId` и имеющиеся идентификаторы файла, контекст чата, двоичное содержимое |

Вложения приёмки по-прежнему используют `/defects/entries/add` с документом акта.
Новый `/acceptance/entries/add` создавать не нужно. `clientEntryId` в методы
`start/complete` не добавляется.

Необходимо подтвердить:

1. Повтор уже принятого запроса возвращает первоначальный успешный результат и
   не создаёт второе сообщение, запись, вложение или повторное проведение.
2. Проверка ключа и запись результата атомарны: два одновременных запроса с одним
   ключом не проходят как две новые операции. Локальная блокировка приложения не
   заменяет эту гарантию на сервере.
3. Ключ проверяется с корректным контекстом метода, пользователя и объекта. Чужой
   пользователь не может получить первоначальный результат по известному ID.
4. Если идентификатор повторился с другим содержимым, возвращается определённый
   конфликт (например, HTTP 409), без повторной записи.
5. После потери ответа успешная запись остаётся доступной для идемпотентного повтора.

Клиент делает не более пяти автоматических попыток при временных сбоях. Ручной
повтор сохранённой операции не меняет её идентификаторы и содержимое.

Общее правило по requestId было зафиксировано в `1C_SECURITY_AND_CONTRACT.md`.
Для приёмки и дефектовки оно уточнено в `QUEUE_CONTRACT_1C_2026-10-22.md`.
Для постоянной очереди чатов особенно важно подтвердить его на обоих `files/send`
и `messages/send` в реально опубликованной версии. Клиентские тесты этого не доказывают.

## 2. Успех, HTTP 422 и транзакции

- HTTP 200 подтверждает операцию; обязательного нового `entryRef` в ответе клиент
  не требует. Явное `success:false` даже при HTTP 200 не является успехом.
- Возвращать HTTP 200 только после фиксации всей операции. Асинхронное «принято в
  обработку» нельзя выдавать за сохранение без отдельного согласованного контракта.
- До записи файла/сообщения проверить обязательные поля, права, соответствие
  `documentRef` заказу и допустимость состояния документа.
- HTTP 422 должен обозначать непринятую бизнес-операцию. Нельзя сначала записать
  файл, затем вернуть 422 без определённого результата транзакции.
- Если частичная запись сейчас возможна, явно описать этот случай и сделать
  повтор с прежним requestId безопасным; иначе простая смена клиентского ID даст дубль.

Предпочтительный существующий формат ошибки:

```json
{
  "success": false,
  "error": {
    "code": "DOCUMENT_STATE_INVALID",
    "message": "Документ уже завершён. Откройте актуальное состояние."
  }
}
```

Сообщение должно объяснять исправимое действие, но не содержать стек 1С, пароли,
токены, серверные пути или данные чужих документов. Технический requestId можно
передавать отдельно, не меняя его. Нельзя маскировать отказ постоянным индикатором
«отправляется»: приложение сохраняет пакет и показывает реальную ошибку.

Если нужно изменить содержимое отклонённой операции, это отдельная пользовательская
коррекция после выяснения результата прежней записи, а не автоматическое изменение
сохранённого пакета с прежним идентификатором.

## 3. Правила завершения документа

Клиент ждёт подтверждения обязательных локальных частей. Со стороны 1С всё равно
нужны собственные проверки:

- заказ и документ связаны друг с другом;
- текущий сотрудник имеет право на операцию;
- обязательные поля и записи присутствуют;
- повтор успешного complete с тем же requestId не проводит документ второй раз.

Отдельный маршрут статуса не является условием установки этого релиза: сохранён
уже согласованный путь идемпотентного повтора. Если 1С не может гарантировать его,
об этом нужно сообщить до массового использования очереди.

## 4. Личность пользователя и доступ к разделам

Это существующий вопрос безопасности, а не новый формат авторизации релиза.
В клиенте есть ручной ввод MAX ID; Node-прокси использует общий интеграционный
секрет. Сам факт наличия корректного `X-ITUS-Token` подтверждает интеграцию, но не
личность сотрудника, чей `userId` указан в теле.

Разработчику необходимо ответить: **чем опубликованный сервис подтверждает, что
человек действительно владеет этим MAX ID при входе через Android/Safari/Яндекс?**

- Для MAX WebApp проверять подпись и срок действия `max.webAppData`.
- Для самостоятельного приложения нужен проверяемый вход и серверная сессия
  (например, одноразовое подтверждение через связанный MAX-аккаунт). Точный формат
  такой сессии согласуется отдельным изменением клиента и 1С.
- Если сейчас достаточно произвольного числового ID без проверки, до общего
  открытия всем пользователям требуется доработка авторизации. 2.7.13 не вводит
  выдуманную сессию, которую 1С не умеет проверять, и не объявляет этот вопрос решённым.
- Права на каждый ЗН, чат и документ проверяются на сервере независимо от видимости
  вкладок. Для обычного сотрудника `availableTabs: []` означает отсутствие доступных
  разделов; отсутствие/пустой список больше не раскрывает все вкладки.
- Сохранено подтверждённое поведение администратора: опубликованная 1С для согласованного
  пользователя возвращает нормализованную точную роль `admin` и пустой availableTabs.
  Точная серверная роль `admin`/`administrator` остаётся явным разрешением всех разделов.
  Подстрока вроде «админ-помощник» такого разрешения не даёт. Для обычных ролей
  сервер должен вернуть реальный разрешённый список.

## 5. Push

Новые маршруты не нужны. Для subscribe подтверждать сохранение установки:

```json
{"success":true,"data":{"registered":true}}
```

Регистрация идемпотентна по пользователю/платформе/clientInstanceId; Android FCM и
Web Push остаются раздельными. Для Web продолжает действовать доверенный серверный
`X-ITUS-Push-Context`. Клиент теперь повторяет неудавшийся серверный этап регистрации,
а не считает получение FCM token подтверждением записи в 1С.

## 6. Скорость и безопасная диагностика

В проверенных журналах рабочей 2.7.11 встречались 35-секундные таймауты входа,
поиска и notifications/poll. Это требует измерения в 1С; одна смена анимации не ускорит метод.

На один requestId фиксировать маршрут, время начала/окончания, HTTP-код и безопасный
error.code. Для истории/вложений добавить агрегаты: messageCount, attachmentCount,
base64AttachmentCount, base64Bytes, responseBytes, durationMs. Не записывать тексты,
ФИО, ссылки, токены, Base64 и содержимое файлов. Node 2.7.13 добавляет в технические
строки только числовые requestBytes/responseBytes и прежний requestId.

При проверке обнаружено: запрос `/auth/max` без заголовка `x-itus-request-id`
возвращает необработанную ошибку модуля 1С вместо JSON. Штатный клиент заголовок
передаёт. На сервере нужно проверять его наличие и возвращать безопасный HTTP 400
с JSON, а не техническую трассировку.

История чатов с `includeAttachmentContent:false` не должна возвращать тяжёлый
contentBase64; файл загружается отдельно по существующему маршруту. Проверить
постраничность, запросы к регистрам и выборку поиска по всем доступным сотруднику ЗН.

## 7. Большие видео — отдельный этап

В стабилизационном релизе 2.7.13 сохранён подтверждённый предел 15 МиБ на файл.
Текущая передача — JSON/Base64, Node 30 МиБ, Nginx для I-MAX 32 МиБ, клиент/прокси
35 секунд. Ветка 2.7.12 с одним снятым клиентским пределом не объединена с этим
релизом: она не обеспечивала надёжную отправку больших видео.

Для расширения нужно подтвердить пределы HTTP-сервиса 1С и время обработки. Для
роликов произвольного практически допустимого размера согласовать отдельную загрузку:

1. создание сессии загрузки с владельцем, размером и контрольной суммой;
2. последовательные части со стабильными номерами, повтор без дублей;
3. запрос принятых частей после обрыва;
4. финальная проверка целостности и возврат fileRef;
5. привязка fileRef к записи/сообщению и complete только после фиксации.

Это предложение для согласования, **не существующие новые методы и не обязательная
миграция для 2.7.13**. Перед реализацией определить, где временно хранятся части,
кто их удаляет, квоты, сроки и права доступа. Нельзя объявлять неограниченную
загрузку только на основании отсутствия проверки размера в интерфейсе.

## 8. Живая приёмка со специалистом 1С

На согласованных тестовых документах проверить:

1. Три различимых фото → немедленное завершение → переход к другому ЗН: три файла
   у исходного документа, одна команда завершения после подтверждений.
2. 1С сохранила файл, ответ потерян: повтор с тем же requestId/clientEntryId,
   в базе одна запись и один файл.
3. Ошибка среднего файла: complete не вызывается; после разрешённого повтора
   успешно принятые части не дублируются, complete продолжается.
4. Закрытие и открытие приложения, потеря/возврат сети: сохранённые операции
   восстанавливаются с прежними ID.
5. Сотрудник А выходит, входит Б: операции А не отправляются от имени Б.
6. Те же сценарии для внутренних и клиентских чатов, включая один отказ файла.
7. Повтор complete после потери ответа не приводит к повторному проведению.

Результат передать без секретов: версия сервиса 1С, время, маршрут, requestId,
clientEntryId/clientMessageId, HTTP-код, число фактических записей/файлов и факт
завершения. Клиентские автоматические тесты уже воспроизводят сбои на заглушке,
но не заменяют проверку транзакций вашей опубликованной базы.
