# I-MAX 2.8.0 — изменения для разработчика 1С

Дата: 29.10.2026. База приложения: 2.7.13 / `22e37e2a4b50d2788ad4a97c429d942a859f4bc3`.

## 1. Признаки акта в списке и карточке ЗН

Проверенный production `/orders/list` возвращает `defectDocumentRef`, но не возвращает
признаки акта приёмки. Ссылка на дефектовку не доказывает наличие акта.

Добавить следующие поля в каждый объект существующих `/orders/list`, `/orders/search`
и `/orders/get` (новые маршруты не нужны):

```json
{
  "acceptanceExists": true,
  "acceptanceCompleted": true,
  "acceptanceDocumentRef": "ссылка существующего акта"
}
```

- Акт отсутствует: `false`, `false`, пустая строка.
- Акт создан, не завершён: `true`, `false`, реальная ссылка.
- Приём завершён: `true`, `true`, реальная ссылка.
- Значения boolean, не строки `"true"`/`"false"`.
- Рассчитывать из существующего документа, не из состояния текущего читателя.
- Не создавать акт при чтении списка/карточки.

Клиент показывает зелёную точку при подтверждённом наличии акта, красную при явном
`acceptanceExists:false`. При отсутствии данных показывает серую точку «Статус не
передан 1С», чтобы не выдавать неизвестное за отсутствие документа.

После успешных start/complete факт сохраняется также на устройстве в контексте
сотрудника/API/ЗН. Серверные явные значения имеют приоритет. Чтобы статусы были
достоверны сразу у всех сотрудников и после смены телефона, нужны поля выше.

## 2. Завершённая приёмка

По решению владельца повторное создание после завершения запрещено: кнопка становится
неактивной. Завершение с прежним `requestId` по-прежнему должно быть идемпотентным.

Для старых клиентов и ситуаций устаревшего списка рекомендуется структурированный отказ:

```json
{"success":false,"error":{"code":"ACCEPTANCE_ALREADY_COMPLETED","message":"Прием автомобиля завершен!"}}
```

Клиент 2.8.0 понимает этот код и уже используемое точное сообщение. После такого ответа
он блокирует кнопку; не создаёт новые идентификаторы и не повторяет start. Бизнес-проверку
в 1С оставлять, её нельзя заменять только отключённой кнопкой.

## 3. Добавление дефекта из МП

Кнопка «Добавить дефект / фото / видео» в МП открывает существующую дефектовочную
ведомость через прежние методы `/orders/get`, `/defects/start`, `/defects/entries/add`.
Она больше не зависит от временно открытой формы акта приёмки.

Фото самого акта добавляются из формы приёмки. После завершения акта его редактирование
не включается. Новые дефекты и вложения относятся к дефектовке выбранного ЗН.

## 4. Видео без прежнего лимита 15 МиБ

На участке приложение → Node видео теперь передаётся бинарным телом с метаданными.
Node сохраняет его во временный закрытый файл и потоково формирует привычный JSON.
**Для 1С формат не меняется:** `file.contentBase64`, `fileName`, `mimeType`, `sizeBytes`,
существующие `requestId`, `clientEntryId`/`clientMessageId`, ссылки документа/чата.

Применено к `/defects/entries/add`, `/clients/files/send`, `/internal-chat/files/send`.
Новые загрузочные методы в 1С не требуются. Старые JSON-запросы остаются совместимыми.

Проверить и при необходимости увеличить ограничения веб-сервера публикации 1С,
HTTP-сервиса, размера двоичных данных, времени запроса и транзакции. Бинарные 40 МиБ
становятся примерно 53.3 МиБ Base64 плюс JSON. Node не может отменить лимиты IIS/Apache
или лимиты самой 1С. Не включать «успешную» отправку, если файл не записан полностью.

В приложении нет фиксированного порога размера для видео. Практические ограничения:
свободное место IndexedDB, место на сервере, сеть, таймаут до 20 минут и пределы 1С.
Фото и обычные документы сохраняют прежний лимит 15 МиБ; профиль сжатия фото не изменён.

На Node одновременно обрабатываются до двух видео. Остальные получают временный 503
и используют существующие повторы очереди. Видео не загружается целиком в память Node;
временный файл удаляется после ответа/ошибки, остатки аварийного процесса старше суток
очищаются при запуске и ежечасно. Сохраняется запас свободного места 256 МиБ.

Существующие гарантии идемпотентности и атомарности из `1C_STABILIZATION_2.7.13.md`
остаются обязательными. Смена транспорта не является разрешением частичной записи
перед HTTP 422 или создания дубля при потере ответа.

## 5. Что проверить вместе

1. Список ЗН: отсутствующий/созданный/завершённый акт, второй сотрудник и другое устройство.
2. Завершённый акт: кнопка неактивна; повторный start не уходит.
3. Добавить дефект из МП после завершённой приёмки: правильная ведомость и ЗН.
4. Видео 20, 40 и 100 МиБ: приёмка, дефектовка, оба чата; сравнить длину/контрольную сумму.
5. Прерывание сети и повторный вход: прежние ID, один файл, complete только последним.
6. Открыть старую вкладку одновременно с новой: не потерять существующие операции.

Локальные проверки прошли на синтетическом видео >40 МиБ и тестовом приёмнике.
Это не утверждение, что опубликованная 1С уже принимает видео такого размера:
реальные файлы в рабочие документы при подготовке релиза не отправлялись.
