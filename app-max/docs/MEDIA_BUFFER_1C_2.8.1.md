# I-MAX 2.8.1 — изменения обмена с 1С

Контур этого выпуска: только `aa6_ea_test9`. Подключение `aa6_ea` не выполняется.

## Отправка файлов

Маршруты 1С остаются прежними:

- `/defects/entries/add` — вложения приёмки и дефектовки;
- `/clients/files/send` и `/internal-chat/files/send` — вложения чатов;
- `/acceptance/complete` и `/defects/complete` — завершение.

Подготовленный файл до **10 485 760 байт включительно** идёт существующим
транспортом. Более крупный файл сначала передаётся в приватный S3-буфер.
Порог фотографии определяется после сжатия. Маршрут сохраняется в локальном
пакете и не меняется при повторе.

Из S3 сервер передаёт в 1С **полный файл** в прежнем `file.contentBase64`.
Ссылки на S3 не заменяют файл в базе. `requestId`, `clientEntryId`/
`clientMessageId`, `clientFileId`, время и тело операции сохраняются.
Новые поля S3 и секреты в контракт 1С не добавляются.

1С не должна сохранять Base64 в журнале обмена. После декодирования сохраняется
двоичный файл. Следует проверить реальные ограничения публикации и таймауты:
Base64 увеличивает тело примерно на треть; отсутствие лимита 15/20 МиБ в
приложении не отменяет доступное место и ограничения HTTP-сервера 1С.

## Обязательные гарантии существующих методов

1. HTTP 200 / `success:true` означает, что транзакция **зафиксирована**.
2. Повтор того же `requestId` и того же делового содержимого возвращает
   первоначальный успешный результат. Он не создаёт повторную запись и не
   возвращает 409 только из-за факта повтора.
3. Дополнительно уникальны `clientEntryId` и `clientMessageId` в пределах
   соответствующего документа/чата. Проверка идентификатора и запись файла
   выполняются атомарно, включая параллельные запросы.
4. Идемпотентность относится отдельно к обоим методам `complete`.
5. Подпись дедупликации делового запроса не должна зависеть от обновившейся
   авторизации, версии клиента или транспортных HTTP-заголовков.
6. 422 — данные отклонены; после ошибки нельзя оставлять частично проведённую
   запись файла. 409 допустим при **другом** содержимом под прежним ID.

Серверный обработчик делает максимум пять безопасных автоматических попыток
до передачи в 1С (например, при недоступном соединении или S3), сохраняя
идентификаторы. После потенциальной записи и потери ответа слепой повтор
отключён: фактическая идемпотентность текущей 1С не прошла живую проверку.
Новый постоянный журнал Node возвращает сохранённую квитанцию без повторной
записи в 1С; неопределённый результат сохраняется для сверки. 422 останавливает отправку; 409 помечает результат неоднозначным
и требует сверки. Новые IDs для обхода ошибки не генерируются. Отдельный метод
проверки результата в текущей публикации не предполагается существующим.

Рекомендуемое дополнение: `POST /operations/status` по `requestId` с результатом
`not_found|processing|committed|rejected`, ссылками на запись и файл. До его
согласования автоматического разрешения неоднозначного 409 нет.

## Порядок завершения

После нажатия завершения создаётся команда с зависимостями от всех ещё не
подтверждённых частей документа. Сервер ждёт квитанции 1С и для малых файлов,
и для файлов S3. При ошибке обязательной части `complete` не вызывается.
Закрытие приложения после полной загрузки в S3 не останавливает импорт.
Файлы, оставшиеся только на телефоне, требуют повторного открытия приложения.

## Чтение вложений и истории

Для обычной истории `includeAttachmentContent:false` должно исключать Base64.
Чаты уже проверялись с этим режимом; 1С следует сохранить это поведение.

Для `/defects/start` нужно подтвердить поддержку:

- `existingDocumentRef` — открыть существующий документ;
- `includeAttachmentContent:false` — вернуть только записи и метаданные;
- `includeAttachmentContent:true` + `attachmentRef` (+ `entryRef`) — вернуть
  содержимое **только выбранного файла**, с его фактическим `fileRef`, MIME,
  именем и размером. Повторное чтение не создаёт документ.

Для чатов запрос выбранного вложения остаётся `/messages/list` с
`messageRef`, `attachmentRef`, `includeAttachmentContent:true`.
Ответ должен содержать точные ссылки выбранного сообщения и файла.

Подключённое устройство получает файл через потоковый преобразователь Node:
он сохраняет двоичные данные во временный закрытый файл и отдаёт браузеру
обычный файл с поддержкой HTTP Range. Base64 целиком в память браузера не
попадает. Если 1С возвращает несколько файлов, преобразователь отбрасывает остальные
на сервере и выдаёт только выбранный файл с проверкой ссылки сообщения.
Содержимое остальных вложений не попадает в браузер.
Если 1С игнорирует фильтр вложения дефектовки, этот метод необходимо доработать
либо согласовать отдельный двоичный `/files/content`.

## Авторизация и диагностика

S3-канал требует устройство, подключённое одноразовым кодом администратора.
Пользователь и права на объект проверяются сервером. S3-ключи не передаются
в приложение. Это защищает новый медиаканал; прежний вход основного приложения
по одному MAX ID не становится проверенной авторизацией MAX. Проверка
подписанного `webAppData`/подтверждённой личности остаётся задачей интеграции.

Для разбора ошибки нужны: UTC-время, маршрут, `requestId`, `clientEntryId`/
`clientMessageId`, HTTP-код и безопасный код ошибки, результат транзакции.
Не передавать Base64, переписку, токены и S3-ключи.

проверки результата; затем лёгкая история/выбранный файл и сохранение метаданных.
