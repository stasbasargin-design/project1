# I-MAX 2.9.1: сообщения и пересылка дефектовки

Подтверждённая база: production / origin/main 2.9.0, `0474520e9322ca032750d2e07cbbb596bc03da10`.

## Пользовательское поведение

1. Поле сообщения в обоих мессенджерах растёт при переносах текста до шести строк, с дополнительным ограничением по доступной высоте экрана. Затем прокручивается само поле. Удаление текста уменьшает высоту. Enter по-прежнему отправляет, Shift+Enter добавляет перенос; составление текста IME не отправляет сообщение.
2. Фото и видео дефектовки открываются отдельным верхним окном. Закрытие крестиком, Escape или Android Back закрывает только просмотр. Ведомость, её позиция, черновик и отметки сохраняются без повторного запроса документа.
3. Только в МП при наличии существующего разрешения на клиентские чаты можно отметить текстовые записи и фотографии. Видео не пересылаются этим действием. Затем: список выбранного → загрузка доступных чатов → явный выбор получателя → подтверждение. Получатель автоматически не назначается.

Пересылка создаёт обычные новые сообщения. Автором новых сообщений выступает отправляющий сотрудник по действующему контракту чата. Исходная запись, её автор и исходный файл не изменяются. Фото копируется в сохранённом качестве, без повторного сжатия. Это не обещание дедупликации между разными документами/чатами в хранилище 1С: создаётся обычное новое вложение чата.

## Существующий контракт 1С — новые методы не требуются

- `/clients/topics/list` с `status: "active"` возвращает доступные текущему сотруднику чаты с настоящим `topicRef`.
- `/clients/messages/send`: `topicRef`, `topicId`, стабильный `clientMessageId`, `text`.
- `/clients/files/send`: `topicRef`, `topicId`, стабильный `clientMessageId`, `kind: "photo"`, `file`.
- Файл использует действующие поля `fileName`, `mimeType`, `sizeBytes`, `clientFileId`, `contentBase64`; для крупных фото применяется существующий S3-транспорт.
- Если байтов фото нет в уже загруженной ведомости, используется существующий механизм получения выбранного вложения `/defects/start` с действующими ссылками документа/строки/файла. Создание документа, добавление строк, проверка и завершение при пересылке не вызываются.

1С дорабатывать для этой функции не нужно при работоспособности этих существующих методов. Права на чтение и отправку по-прежнему проверяет 1С; приложение не расширяет доступ сотрудника.

## Надёжность

Все выбранные части подготавливаются до сохранения пакета в существующую IndexedDB-очередь чата. До подтверждения локального сохранения никакая часть пакета не отправляется. Ошибка чтения фото не приводит к отдельной отправке ранее подготовленного текста. Повтор подготовки в том же подтверждении сохраняет идентификаторы. Повторное нажатие во время сохранения не создаёт вторую операцию.

Контур, сотрудник и документ фиксируются при выборе. Смена сотрудника/контура/документа отменяет незавершённую подготовку; уже сохранённые операции остаются у исходного владельца. Схема базы очереди, lease, правила повторов и обработка 422 не изменяются. Закрытие окна после сохранения не означает подтверждённую доставку: результат отражается обычной очередью чата и её отчётом.

## Проверки перед выпуском

- Полный `npm test`, включая реальный браузер и IndexedDB; `npm run build`, `git diff --check`.
- Автоматически: рост/уменьшение, перенос по ширине, предел высоты, каретка, позиция истории и черновик в обоих чатах; просмотр фото/видео в МП, исполнителе и технологе без потери ведомости; отметки технолога не заменяются выбором для пересылки.
- Автоматически: явный получатель, только выбранные текст/фото, исходные байты фото, полный пакет до HTTP-ответа, отсутствие второго пакета при двойном нажатии, стабильные IDs после ошибки подготовки, отсутствие записи в исходную ведомость, смена владельца.
- На max-test: проверка точного SHA файлов и версии. Реальные сообщения клиентам без отдельно согласованного получателя не отправлять.
- Физические Android/iPhone и фактическая доставка пересланных сообщений конкретному клиенту требуют отдельной приёмки; браузерная эмуляция не заменяет проверку устройства.

Production выпускается только после подтверждения владельцем точного SHA 2.9.1. До него production остаётся 2.9.0.
