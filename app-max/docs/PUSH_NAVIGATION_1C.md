# Push-навигация I-MAX: контракт для 1С

## Назначение

Документ описывает данные, которые 1С передаёт при отправке Push, чтобы
мобильное и веб-приложение открывали правильный раздел после нажатия на
уведомление. Существующие HTTP-маршруты и JSON-контракты интеграции не
изменяются.

## Внутренний чат

Для нового сообщения во внутреннем чате передавайте:

```json
{
  "type": "internal_chat_message",
  "topicRef": "GUID_ГРУППЫ_ИЛИ_ЛИЧНОГО_ЧАТА",
  "eventId": "УНИКАЛЬНЫЙ_ID_СОБЫТИЯ"
}
```

`topicRef` — это идентификатор внутренней переписки. В текущем HTTP-контракте
при загрузке истории он передаётся в 1С как `groupRef` и `groupId` в
`/internal-chat/messages/list`. Нельзя передавать имя чата вместо
идентификатора или открывать по этому событию клиентский B2B-чат.

После нажатия I-MAX проверяет авторизацию, открывает вкладку «Чат», находит
переписку по `topicRef` и загружает актуальную историю без содержимого
вложений. Если чата нет в доступных пользователю — отображается безопасная
ошибка без раскрытия данных.

## Запрос контроля качества

Для уведомления технологу передавайте:

```json
{
  "type": "quality_control_requested",
  "orderRef": "GUID_ЗАКАЗ_НАРЯДА",
  "eventId": "УНИКАЛЬНЫЙ_ID_СОБЫТИЯ"
}
```

`orderRef` — GUID заказ-наряда, не его номер. После нажатия приложение
получает ЗН существующим `/orders/get`, открывает вкладку технолога и
загружает форму существующим `/quality/start`. Права доступа остаются на
стороне 1С и приложения.

## Завершение дефектовки

После завершения дефектовочной ведомости передавайте:

```json
{
  "type": "defect_complete",
  "orderRef": "GUID_ЗАКАЗ_НАРЯДА",
  "documentRef": "GUID_ДЕФЕКТОВОЧНОЙ_ВЕДОМОСТИ",
  "eventId": "УНИКАЛЬНЫЙ_ID_СОБЫТИЯ"
}
```

`orderRef` и `documentRef` обязательны. После нажатия приложение загружает
доступный сотруднику заказ-наряд через `/orders/get`, проверяет, что его
дефектовочная ведомость совпадает с `documentRef`, затем получает её данные
существующим `/defects/start`. Несовпадающий, отсутствующий или недоступный
документ не открывается.

## Идентификатор события

Рекомендуется всегда передавать `eventId`. Он предотвращает повторный переход
при повторной доставке одного Push. Если он не передан, приложение использует
тип и целевой идентификатор как временный ключ дедупликации.

Если уведомление открыто до входа пользователя, цель остаётся в памяти
приложения только до успешной авторизации. При выходе она удаляется.

## Авторы сообщений

Для `/clients/messages/list` и `/internal-chat/messages/list` 1С должна
возвращать фактическое имя автора в `authorName`, как описано в
`1C_HTTP_METHODS_RELEASE.json`. Совместимые уже поддерживаемые поля:

1. `authorName`;
2. `senderName`;
3. `from`.

Клиент не подставляет в историю имя текущего пользователя, исполнителя ЗН или
последнего автора. Ответы `/messages/send`, содержащие только `messageRef`,
допустимы: приложение после этого обновляет облегчённую историю и получает
фактического автора из 1С.

## Проверка перед выпуском

1. Отправить Push `internal_chat_message` существующему сотруднику.
2. Нажать Push в открытом приложении, из фона и после холодного запуска.
3. Проверить сценарий отсутствующего или недоступного `topicRef`.
4. Отправить `quality_control_requested` с реальным `orderRef` технологу.
5. Отправить `defect_complete` с реальными `orderRef` и `documentRef` и проверить открытие
   именно этой завершённой дефектовочной ведомости.
6. Проверить отсутствующие, несовпадающие и недоступные пользователю ссылки.
7. Убедиться, что истории клиентского чата от разных сотрудников показывают
   имена из ответа 1С после обновления и повторного открытия.
